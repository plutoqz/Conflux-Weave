## 0. 这一份方案回答的核心问题

1. **研究者面对 Vibecoding 与开源项目时，最迫切的代码痛点是什么？**  
   代码能跑通，但结构像黑盒；AI 辅助生成或开源作者写的代码模块众多，核心算子隐藏较深；实验分支越开越多，难以厘清改动与意图；设计文档很完备，但不清楚代码到底真正实现了多少、有没有空函数或脆弱降级；代码耦合度高、缺乏测试保护，后续微调动辄引发崩溃。
2. **为什么“项目”分区绝不能做成一个粗糙的在线代码编辑器 (Web IDE)？**  
   专业开发者拥有成熟的本地 IDE（Cursor、VS Code、PyCharm 等），不需要在 Web 页面中写大段业务逻辑；研究者需要的是**代码透视镜、学术研读台与质量治理看板**（“理解代码”、“验证设计”、“管控实验”、“安全重构”）。
3. **如何让 Git 演进服务于学术实验而非机械提交流程？**  
   提供“人话版”语义差异分析（Semantic Diff），解释当前分支与主线在算法、参数、Prompt 上的真实实验意图，而不是单纯展示枯燥的增删代码行。
4. **如何实现设计与代码的“闭环审计”？**  
   建立“设计文档/需求规范 ↔ 源码实现 ↔ 测试用例”的三向审计链条，明确标识出“真实完整落地”、“带临时 Mock 的假象实现”和“未实现的空桩函数”。
5. **如何帮助研究者安全解耦代码技术债？**  
   以只读为绝对前提，检测上帝类、循环依赖、环境状态污染等坏味道，并通过 `CodingAgent` 输出具备乐观锁保护、微粒度、可审查核准的结构化补丁。

## 1. 核心设计原则与安全红线

1. **研究者第一原则 (Researcher-Centric Ergonomics)**：
   - 界面呈现重点在“架构全景、技术内幕、理论映射、质量体检”，而非纯文件目录与文本编辑。
   - 所有分析与问答必须实事求是，严格绑定物理文件相对路径与代码行号，严禁无事实根据的幻觉分析。
2. **只读优先与写操作物理核准红线 (Strict Read-Only & Explicit Approval)**：
   - 探查、审计、问答、解构分析全过程为**严格只读**，不触碰本地文件内容。
   - `CodingAgent` 的补丁方案必须显式展示基准哈希、风险级别与 Unified Diff，必须由用户在前端点击“核准并原子应用”；若底层文件在审查期间发生变更，强制以 `409 version_conflict` 阻断。
3. **工作区隔离与越界防护 (Sandbox Safety)**：
   - 严格在登记的项目根目录下操作，拦截任何包含 `..` 或符号链接穿透的路径逃逸（`403 Forbidden`）。
   - 默认排除敏感凭据（`.env`、密钥文件）与大型非代码资产（`.git/`、`.venv/`、`node_modules/`、编译缓存）。
4. **纯本地离线与零外部 CDN 保证 (100% Offline Native)**：
   - 纯原生 Vanilla ESM，不引入外部 CDN 字体或脚本库，不改动已有 16 条运行端点与 SSE 契约。

### 支柱 1：项目全景解构与论文理论映射 (Architecture Deconstruction & Theory Mapping)

针对 Vibecoding 生成的代码或 GitHub Clone 的学术开源代码：

1. **项目技术内幕与全景导读（Onboarding Walkthrough）**：
   - 自动扫描根目录 `README.md`、`pyproject.toml`、核心模块与包入口，一键提炼《项目设计意图与工程全貌》；
   - 梳理组件清单：哪些是服务层（API/CLI）、哪些是核心算法/模型层、哪些是数据管线与存储层。
2. **核心数据流向与模块拓扑提取（Data Flow & Topology）**：
   - 自动分析模块导入关系与调用链，生成标准的 Mermaid 架构拓扑图与数据流动示意图；
   - 讲清关键数据结构在各个处理阶段的转换链路。
3. **论文/理论与代码映射（Theory-to-Code Mapping）**：
   - 建立论文理论与源码的映射索引，例如：
     - *“论文中的公式 (3) 缩放点积注意力，对应 `src/conflux_weave/retrieval.py:L135-139`”*；
     - *“论文第 4 节的 RRF 倒数排序融合机制，对应 `hybrid_retrieval.py:L210`”*；
   - 针对初学者或跨学科研究者，提供设计决策动机解析（“为什么这里要采用双模态降级而不是直接报错？”）。
4. **依赖拓扑与环境透视**：
   - 区分核心直接依赖、底层重型依赖与间接依赖，标注其在系统中的关键用途，识别是否有未使用的多余库。

### 支柱 2：Git 实验谱系与语义变更管理 (Git & Branch Lineage)

针对研究者高频切换分支、调整算法超参、微调 Prompt 的实验过程：

1. **分支语义差异（Semantic Branch Diff）**：
   - 摒弃单纯的代码行 `+` / `-` 展示，提供“人话版”实验意图分析：
     - *例如：“`feat/multimodal-rrf` 分支相比 `main`：新增了 LanceDB 图像索引表族，在检索中加入了 RRF 排序融合逻辑，共影响 4 个核心文件；新增 12 个自动化测试。”*
2. **当前工作区状态与实验快照建议（Dirty Workspace Guard）**：
   - 智能归类当前未提交的修改：
     - 算法/核心逻辑修改（High Impact）；
     - 配置与参数调试（Config Adjustment）；
     - 文档与测试用例（Documentation & Verification）；
   - 给出符合 Conventional Commits 规范的语义化提交信息建议，提醒研究者在开启新实验前保存稳定检查点。
3. **关键实验与基准历史谱系**：
   - 从 Git Log 中提炼关键里程碑节点（如：`首次通过回归测试`、`冻结 P2 准入评估`），支持一键对比不同实验提交间的代码演进。

### 3. 支柱 3：功能实现与设计契约审计 (Implementation & Contract Audit)

解决“设计方案写得天花乱坠，实际代码可能只是空架子或假实现”的失真问题：

1. **设计文档 vs 真实代码一致性审计（Design vs. Code Audit）**：
   - 读取项目中的设计文档（如 `docs/design/`）、需求说明或用户自定义的验收条目；
   - 智能静态扫描工程源码，对每条规划能力给出**真实度分级标签**：
     -  **`fully_implemented`（完整闭环）**：业务逻辑完整，具备状态持久化、异常分支，且有单元测试断言覆盖；
     -  **`partially_implemented`（部分落地 / 存在脆弱降级）**：接口已打通，但关键分支使用了硬编码 Mock、静态写死字段或缺少必要校验；
     -  **`stub_or_todo`（空占位 / 桩函数）**：仅有函数签名、`pass`、`TODO` 注释或直接返回空对象；
     -  **`unimplemented`（完全缺失）**：设计文档中有明确规约，但源码中未发现任何对应落点。
2. **边界与容灾韧性审计**：
   - 重点检查高危脆弱点：外部 Provider 超时、网络请求断开、畸形响应 JSON、超长输入截断、并发竞争等是否具备防御性兜底。

---

### 支柱 4：代码风格、耦合度与质量体检 (Code Health & Style)

针对 AI 辅助编程（Vibecoding）极易产生的“代码膨胀、高耦合、全局状态污染”问题：

1. **模块耦合度与复杂度诊断**：
   - **单文件超长与上帝类（God Class）**：标记行数超过 800 行且承担多重异构职责的文件；
   - **循环依赖与深度嵌套**：检测跨层级的双向依赖关系；
   - **代码冗余度**：检测 AI 生成中常见的函数复制粘贴与微小变体。
2. **隐式状态与环境污染体检**：
   - 检测是否有未经清理的全局变量、单例缓存、直接 `os.environ[...] = ...` 污染进程环境的高危模式；
   - 检查资源泄漏（未关闭的文件句柄、临时目录未销毁）。
3. **测试防护网评估**：
   - 统计核心逻辑的代码行与测试用例的映射覆盖情况；
   - 给出有针对性的“最小完备测试建议”（Targeted Test Advice），避免盲目追求无意义的覆盖率数字。
4. **渐进式解耦重构补丁（Refactoring Proposals）**：
   - `CodingAgent` 针对发现的高耦合模块，输出细粒度、低风险的拆分建议（如：将数据转换函数提取到纯函数工具模块），并附带 Unified Diff 与前置哈希检查。

---

### 支柱 5：多项目与进度里程碑管理 (Multi-Project & Progress Tracking)

针对研究者同时推进多个实验项目、论文复现仓库与自研原型的场景：

1. **多项目统一工作区（Multi-Project Hub）**：
   - 一键登记与快速切换不同项目（包括当前工程、外部 Clone 仓库、临时 Demo 目录）；
   - 卡片式看板汇总：项目路径、当前活跃分支、Clean/Dirty 状态、代码行规模、主要编程语言、最近一次实验时间。
2. **进度与里程碑仪表盘**：
   - 关联项目的阶段性交付目标（如 P0 基础、P1 论文获取、P2 多模态、P3 项目工作台）；
   - 直观量化当前阶段的实现进度、测试通过率与待办项。

## 3. 数据合同与架构落点

### 3.1 核心数据结构

```python
# 1. 审计条目与审计报告
@dataclass
class AuditFinding:
    finding_id: str
    category: str  # implementation_gap | coupling_smell | state_leak | security_risk | test_gap
    severity: str  # high | medium | low | info
    title: str
    description: str
    target_file: str
    line_number: int | None = None
    snippet: str = ""
    recommendation: str = ""

@dataclass
class ProjectAuditReport:
    report_id: str
    project_id: str
    summary: str
    implementation_score: int  # 0 - 100
    health_score: int          # 0 - 100
    findings: list[AuditFinding]
    checked_rules: list[str]
    created_at: str

# 2. 架构全景解构
@dataclass
class ArchitectureWalkthrough:
    project_id: str
    overview: str
    components: list[dict[str, Any]]
    mermaid_topology: str
    data_flow_description: str
    theory_mappings: list[dict[str, str]]
    dependencies_analysis: dict[str, Any]

# 3. 分支语义差异
@dataclass
class SemanticBranchDiff:
    current_branch: str
    compare_branch: str
    experiment_intent: str
    changed_areas: list[str]
    impact_level: str  # major_experiment | minor_tweak | refactor | docs_only
    file_diff_summaries: list[dict[str, str]]
```

## 5. 实施路线图与验收边界

### 阶段 P3.1：多项目管理、Git 语义差异与目录安全探查（基石层）
- 支持登记、持久化与切换多个本地项目；
- 实现 `GitInspector` 语义化分支差异（比较当前分支与 `main`，输出自然语言改动总结）；
- 实现安全目录树扫描与文件读取，严密阻断 `..` 越界。
- **验收**：单元测试通过，能准确输出任意本地 Git 仓库的语义差异摘要。

### 阶段 P3.2：项目全景解构与论文理论映射（认知层）
- `ProjectAgent` 具备扫描 `README`、`pyproject` 与关键代码并输出 Mermaid 拓扑图能力；
- 建立学术概念/公式与代码文件的关联探测机制；
- 离线状态下具备确定性拓扑与模块摘要生成能力。
- **验收**：在真实学术开源项目（如 Conflux-Weave 或外部论文代码）上，能自动生成准确的架构导读和关键逻辑说明。

### 阶段 P3.3：设计一致性审计与代码健康度体检（治理层）
- 建立 `DesignVsCodeAuditor`，将设计规约与真实代码比对，输出完整闭环、部分实现或空桩函数清单；
- 建立质量诊断规则：上帝类检测、单文件复杂度、隐式环境污染检测；
- 输出结构化的 `ProjectAuditReport`。
- **验收**：能够准确抓取人为埋设的“仅有签名无实现的空函数”或“高耦合上帝类”坏味道，并给出准确行号。

### 阶段 P3.4：Workbench 工作台前端重塑与受控解耦闭环（交互层）
- 落地三栏演播室布局（左侧项目与分支导轨、中间架构拓扑与审计看板、右侧研读与体检智能体）；
- 接入 Mermaid 拓扑图渲染（本地无外部 CDN 依赖）；
- `CodingAgent` 支持针对体检发现的问题生成解耦建议与原子核准补丁；
- 全视口（1440x900 到 390x844）响应式走查与全量回归测试。
- **验收**：通过全量测试（556+ 全部保持通过），浏览器走查无溢出、无控制台报错。
