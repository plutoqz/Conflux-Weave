## 1. 阶段定位

### 1.1 P0 与 S0 的含义

- `P0` 是当前最高产品优先级：先让论文研究链路具备可复用的 Agent、Context、Tool、Workspace 和通信底座。
- `S0` 是 v0.3 的首个实施阶段：只实现第一条论文研究纵向链路必需的最小 Harness，并证明它能接入现有 Runtime 和 Workbench。
- S0 不是 v0.3 P0 全部愿景的同义词，也不以一次完成完整多智能体、完整 RAG、MCP、Memory 或前端重写为目标。

S0 采用：

```text
薄 Harness
  + 一个通用任务入口
  + 一个 ResearchAgent fixture
  + 一个确定性 Tool fixture
  + 一个可持久化 Context Bundle
  + 一组 SQLite 通信消息
  + 一个用户可见结果
```

S0 完成后进入 S1“论文研究工作台”，在同一 Harness 上接入真实论文获取、完整 RAG 和引用验证，而不是继续横向扩建基础设施。

### 1.2 阶段目标

在不建立第二套运行状态、不引入分布式组件、不重写现有论文 Runtime 的前提下，实现并验证：

```text
用户请求
-> Router 形成通用任务
-> Orchestrator 分配给 ResearchAgent fixture
-> 代码生成 Context Bundle
-> Agent 通过 Tool Gateway 调用确定性工具
-> 结果写入 Artifact / Workspace
-> 通信消息与 Run 状态持久化到 SQLite
-> Workbench 可在刷新或重启后读取状态与结果
```

### 1.3 可证伪主张

`H-S0-01`：现有单 FastAPI、单 SQLite、单 Worker 和本地 Artifact Store 足以承载一个框架无关、可恢复的最小 Agent Harness；新的通用任务不需要把 `query/search_query/max_results` 等论文专用字段固化到 Server 或 Harness 合同中，同时现有论文发现路径保持兼容。

以下任一情况会否定 S0 完成：

1. Harness 只能通过论文专用参数运行，无法表达第二类未来任务。
2. Manager、Agent 或前端维护了与 SQLite 冲突的权威 Run 状态。
3. Context 只能依赖进程内对象或完整聊天历史，服务重启后不可重建。
4. Agent 之间传递大段自由文本，而不是 Artifact、Evidence 或 Workspace 引用。
5. Workspace URI 可以越权访问根目录之外的文件，或 `system` 区域可被写入。
6. 消息在重复提交、进程重启或 Event 重放时产生重复副作用。
7. 为完成 fixture 被迫引入 LangGraph、Redis、Kafka、向量数据库或第二个服务。
8. 现有论文发现、取消、恢复、Workbench 或 Artifact/Evidence 测试发生未解释回归。

## 2. 当前事实与判断边界

### 2.1 已确认事实

- 当前分支为 `main`，`HEAD` 与 `origin/main` 均为 `c9def66744f1368e8249783f3b549a81f2ec8860`，方案形成前工作树干净。
- `uv run pytest -q` 当前结果为 `269 passed, 1 warning`；warning 来自 Windows 上 `.pytest_cache` 和临时目录清理的权限问题，不是测试失败。
- `core/contracts.py` 已有 `TaskSpec`、`BudgetLedger`、`RunRecord`、`StepRecord` 和 Run/Step 生命周期。
- `evidence/contracts.py` 已有 `ArtifactRef`、`SourceSnapshot`、`EvidenceRef`、`Claim`、`Citation` 等证据合同。
- `runtime/artifacts.py` 已有本地内容寻址、SHA-256 校验和原子写入。
- SQLite Runtime 已有 Task、Run、Step、Attempt、Lease、Event、Budget、SideEffect、Recovery 和 Delivery 的权威持久化。
- `server.py`、SSE、`WorkerLoop` 和 Workbench 可以复用，但 `RuntimePort.submit()` 及提交 API 仍绑定论文发现参数。
- 现有 `fixed_workflow.py` 是历史离线验证工作流，`durable_paper_runtime.py` 是论文领域 Runtime；二者都不是通用 Agent 合同。

### 2.2 推断

- 当前最主要的架构缺口不是再做一套 Runtime，而是补齐 Runtime 之上的 Agent、Context、Tool、Workspace 和通信合同，并用 Adapter 接入现有论文能力。
- SQLite Event 可以继续承担用户进度投影，但面向 Agent 的可寻址、幂等通信需要独立的消息记录，不能只依赖自由格式 `detail_json`。
- 在只有一个真实执行角色时使用 LLM Manager 不会增加产品价值；S0 的 Manager 应先是确定性 Orchestrator，S1 出现研究、验证等真实角色协作后再决定是否加入模型规划。

### 2.3 待验证假设

- 在不改写现有迁移的情况下，新增 append-only `agent_messages` 表可以满足 S0 的通信查询与重放需求。
- `LocalArtifactStore` 与最小 Workspace Adapter 可以共用同一数据根，但分别保持“不可变内容”和“可寻址工作空间”的语义。
- 现有 Workbench 只需小幅增加通用任务类型和 Agent 状态投影，无需在 S0 重构前端状态管理。

这些假设必须在对应子阶段通过合同、迁移、重启和浏览器测试验证；失败时按第 11 节停止，不用 Prompt 或特判绕过。

## 3. 方案比较与决策

| 方案 | 做法 | 收益 | 主要问题 | 决策 |
|---|---|---|---|---|
| A. 完整 Harness 先行 | 一次实现全部 Agent、VFS、Tool、MCP、Memory、并行调度和完整前端 | 概念完整 | 首次交付慢，合同缺少真实消费者，极易重现概念过载 | 不采用 |
| B. 薄 Harness + 纵向闭环 | 只实现首条论文研究链路使用的公共合同，用 fixture 验证后立即进入真实功能 | 最快暴露合同问题，复用现有资产，便于连续演进 | S0 能力面有限，后续按真实需求扩展合同 | 采用 |
| C. 直接堆叠论文功能 | 先在现有 Runtime 中加入 RAG 和更多 Agent，之后再抽象 | 短期页面功能增长快 | 继续扩大论文专用耦合，后续迁移和观测成本高 | 不采用 |

选择 B。S0 的抽象准入标准只有一条：必须被 S0 fixture 或现有兼容路径实际使用。没有消费者的字段、接口和服务不进入本阶段。

## 4. 资产处理策略

| 现有资产 | S0 策略 | 边界 |
|---|---|---|
| `core` Task/Run/Step/Budget | 直接复用 | 不复制第二套生命周期或预算账本 |
| `evidence` Artifact/Evidence/Claim/Citation | 直接复用 | 新合同只保存引用，不复制 Evidence 正文 |
| `LocalArtifactStore` | 直接复用并由 Workspace 发布调用 | Artifact 仍不可变；Workspace 文件不冒充 Artifact |
| SQLite Attempt/Lease/SideEffect/Recovery | 直接复用 | 不建立新的调度数据库或重试语义 |
| SQLite `run_events` | 作为用户进度投影继续复用 | Agent 消息使用结构化记录并投影必要事件 |
| `server.py`、SSE、`WorkerLoop` | 通过通用 Orchestrator Port 改造复用 | 保留 `/api/v1/tasks/research` 兼容合同 |
| Workbench | 小幅改造复用 | S0 不做导航、视觉体系或前端框架重写 |
| `durable_paper_runtime.py` | 通过兼容 Adapter 接入 | 不在 S0 泛化其内部 Step 或重写论文逻辑 |
| `fixed_workflow.py`、bounded Planner 与历史评估 | 隔离保留 | 可作回归证据，不作为新 Agent 抽象基类 |
| v0.2 deprecated 文档、冻结数据和历史验收 | 只读保留 | 不修改路径、内容、哈希或历史结论 |
| Dense/Reranker、Memory、MCP、完整多 Agent | 延后到真实切片 | 不为未来能力预建空实现 |

## 5. S0 最小合同

合同建议集中在 `src/conflux_weave/harness/contracts.py`，保持标准库实现、框架无关和显式 `schema_version`。当真实消费者增多并产生独立变化频率时再拆包。

### 5.1 `AgentProfile`

用途：声明一个可被调度的 Agent 能力版本，不保存运行状态。

最小字段：

```text
agent_type, version, description
accepted_task_kinds
allowed_tool_ids
default_budget
```

S0 只注册 `research_fixture@v1`，不预建 Manager、Writer、Verifier、CodingAgent 等空 Profile。

### 5.2 `AgentTask`

用途：Manager/Orchestrator 向 Agent 发出的单次可追踪任务。

```text
agent_task_id, run_id, step_id
task_kind, objective, completion_criteria
context_ref
input_refs, allowed_tool_ids
budget
idempotency_key
```

`objective` 可以是自然语言，但输入正文、大型文档和工具结果必须通过引用提供。

### 5.3 `AgentResult`

用途：Agent 对一个 `AgentTask` 的唯一终结或等待输入结果。

```text
agent_task_id
status = completed | partial | needs_input | failed | cancelled | terminated
summary
output_refs, evidence_refs
error_ref, stop_reason
```

token、耗时和工具调用仍由 Runtime/Attempt/预算账本记录，不在 Result 中建立第二份权威计数。

### 5.4 `ContextBundle`

用途：由代码生成一次 Agent 调用所需的有限上下文，并可从 Artifact 重建。

```text
context_id, agent_task_id, schema_version
identity
objective
state_snapshot
input_refs, evidence_refs, workspace_refs
available_tool_ids
constraints, completion_criteria
created_at
```

约束：

- `state_snapshot` 是生成时刻的事实投影，不拥有 Run 状态。
- Bundle 序列化后写入 Artifact，`AgentTask.context_ref` 指向该 Artifact。
- 默认传 L0/L1 摘要与引用；S0 不实现自动摘要或上下文压缩算法。
- Prompt 模板不是领域合同，后续由模型 Adapter 按 Bundle 渲染。

### 5.5 `ToolSpec` 与 `ToolResult`

`ToolSpec` 最小字段：

```text
tool_id, version, description
input_schema, output_schema
side_effect_class
required_permissions
timeout_seconds
```

`ToolResult` 最小字段：

```text
tool_call_id, tool_id, agent_task_id
status
output_refs, evidence_refs
error_ref
started_at, finished_at
```

S0 Tool Gateway 只注册确定性 fixture tool。所有输出先 Artifact 化，消息只传引用。Tool Gateway 必须复用现有 SideEffect 与预算语义。

### 5.6 `MessageEnvelope`

```text
message_id, run_id, agent_task_id
sender, recipient
message_type
causation_id, correlation_id
payload_ref
idempotency_key
created_at
```

S0 消息类型仅包括：

```text
task_assigned
status_update
result_submitted
needs_input
failure_reported
terminated
```

Artifact 发布和 Evidence 发现通过 Result 或状态消息中的引用表达；只有真实查询需求出现时再增加独立消息类型。

### 5.7 `WorkspaceRef`

```text
uri
kind = file | directory
revision
media_type
read_only
```

`WorkspaceRef` 是可寻址资源引用；`ArtifactRef` 是不可变、内容寻址的交付或证据引用。二者不可互换，发布操作显式产生 `ArtifactRef`。

## 6. 最小虚拟文件系统

### 6.1 URI 与映射

S0 只支持：

```text
weave://system/<path>                 只读内置资源
weave://projects/<project_id>/<path>  项目持久文件
weave://runs/<run_id>/<path>          Run 上下文与中间结果
weave://scratch/<agent_instance>/<path> Agent 私有临时文件
```

默认映射：

```text
weave://system/*    -> 包内只读资源
weave://projects/*  -> <data_root>/projects/*
weave://runs/*      -> <data_root>/runs/*
weave://scratch/*   -> <data_root>/scratch/*
```

### 6.2 S0 操作面

```text
resolve
read_bytes
write_bytes_atomic
list_dir
publish_artifact
```

`search_files`、外部 mounts、远程对象存储、FUSE、文件监听和跨机器同步不进入 S0。

### 6.3 权限与并发

- 拒绝绝对路径、`..`、非法 URI、根逃逸和经符号链接逃逸。
- `system` 永远只读；`scratch` 仅当前 Agent 实例可写。
- `projects` 与 `runs` 写入必须携带调用者作用域，并使用原子替换。
- 对可能被多个 Agent 修改的文件支持 `expected_revision` 乐观并发；revision 不匹配时返回冲突，不覆盖新版本。
- 用户可见 Markdown 可更新，但每次交付版本必须发布为新的不可变 Artifact。

## 7. SQLite 通信与状态关系

### 7.1 数据模型

新增下一版 append-only migration，创建 `agent_messages`，至少包含：

```text
message_id primary key
run_id, agent_task_id
sender, recipient, message_type
causation_id, correlation_id
payload_ref
idempotency_key unique
created_at
```

不修改任何已有 migration 的内容或 checksum。`agent_messages` 保存协调消息；现有 Run/Step/Attempt 表继续保存权威执行状态。

### 7.2 写入规则

1. 先验证 Run、Step、AgentTask 和 payload Artifact 引用。
2. 在同一 SQLite transaction 中追加 Message，并追加必要的 `run_events` 用户投影。
3. 相同 idempotency key 和相同内容返回已有记录；相同 key 不同内容返回冲突。
4. Manager 按 `(run_id, recipient, message_id)` 查询待处理消息，不使用进程内队列作为事实来源。
5. 消息重放只能恢复协调状态，不能绕过 Attempt/SideEffect 规则重放外部副作用。

### 7.3 不引入的组件

S0 不使用 Redis、Kafka、RabbitMQ、Celery、独立消息服务或多进程 Agent。只有出现单 SQLite 无法满足的真实并发、吞吐或隔离证据时，才提交新的架构决策。

## 8. 分步实施与验收

### S0.0 基线与耦合清单

实施：

- 从 `main@c9def667...` 创建 `codex/v0.3-s0-harness` 实施分支。
- 复核代码、数据库 migration、API、Workbench 和当前测试基线。
- 标出论文专用耦合点与将使用的 Adapter 边界，不生成新的 scope-freeze JSON。

验收：

- 工作树起点可追溯，现有全量测试通过。
- 只记录事实和差异，不修改 v0.2 历史证据。
- 能明确回答“哪些旧模块不改、哪些由 Adapter 包装”。

### S0.1 通用 Harness 合同

实施：

- 新增 `harness/contracts.py` 和公共导出。
- 实现第 5 节合同、枚举、校验和确定性序列化。
- 扩展架构测试，禁止 Harness 合同依赖 FastAPI、Pydantic、LangGraph、Provider SDK 或持久化实现。

验收：

- 每个合同有构造、非法输入、序列化 round-trip 和 schema version 测试。
- 合同只引用现有 `core` / `evidence` 的稳定类型或 ID，不复制其状态。
- 只有 `research_fixture@v1` 这一实际消费者所需字段进入合同。

### S0.2 Workspace URI 与 Local Adapter

实施：

- 新增 URI parser、权限检查和本地映射 Adapter。
- 实现原子写、revision 冲突和 Artifact 发布。
- 为 `system/projects/runs/scratch` 建立最小目录约束。

验收：

- 正常读写、UTF-8/二进制、空目录和重复发布测试通过。
- 绝对路径、路径穿越、符号链接逃逸、跨 Agent scratch 写入和 system 写入均被拒绝。
- 并发 revision 冲突不会静默覆盖文件。
- 同一内容发布得到稳定 Artifact hash，已有 Artifact 校验不回归。

### S0.3 Agent Message 持久化

实施：

- 追加 SQLite migration 和 Repository mixin。
- 实现 Message append、按 recipient 查询、幂等冲突与 Run Event 投影。
- 保持 Run/Step/Attempt 为权威状态。

验收：

- 新数据库和已有 migration 数据库均可升级；旧 migration checksum 不变。
- 消息排序、过滤、重复提交、冲突、重启后重放测试通过。
- Message 与 Event 的 transaction 失败不会留下半条记录。
- 消息重放不重复执行 Tool 或外部副作用。

### S0.4 通用 Orchestrator Port 与兼容 Adapter

实施：

- 定义通用 `TaskSubmission`、`RouteDecision`、`OrchestratorPort` 和 `AgentExecutorPort`。
- 新增 `LegacyPaperRuntimeAdapter`，把现有论文请求翻译为通用任务，但不改写 `DurablePaperDiscoveryRuntime` 内部步骤。
- 让 Server 依赖通用 Port；保留现有 `/api/v1/tasks/research` 请求和响应兼容。
- Router 在 S0 使用确定性规则；未知或歧义请求返回 `needs_input`，不调用 LLM 猜测。

验收：

- Server/Harness 不再把 `search_query/max_results` 作为通用接口字段。
- 现有 Research API、取消、恢复、SSE、Artifact 和 Evidence 行为保持兼容。
- 新任务类型可以通过注册 Route/Executor 接入，不修改 Server 分支判断。
- 不新增第二个 Worker、数据库或 HTTP 服务。

### S0.5 ResearchAgent fixture 纵向闭环

实施：

- 注册 `research_fixture@v1` 和一个确定性只读 Tool fixture。
- 从任务创建 Context Bundle Artifact，追加任务、状态和结果消息。
- Tool 输出 Artifact 化，AgentResult 引用结果，Run/Delivery 正常收束。
- Workbench 展示通用任务类型、当前 Agent 状态、最终结果和失败/等待输入状态。

验收：

- 从 HTTP/Workbench 可完成一次 fixture 请求并打开最终 Artifact。
- 刷新页面、SSE 重连和服务重启后可从 SQLite/Artifact 恢复同一结果。
- fixture 使用 0 次网络、0 次 Provider 调用、0 input/output token；实际工具调用和耗时进入现有预算/诊断。
- Context Bundle、ToolResult、Message 和 AgentResult 可由 `run_id` 追溯。
- 桌面与移动视口无文本溢出、控件重叠或不可操作状态。
- 现有离线 smoke 与全量测试通过。

## 10. 验证与交付证据

### 10.1 验证层级

| 层级 | 重点 | 证明边界 |
|---|---|---|
| 单元测试 | 合同、URI、权限、序列化、幂等 | 局部机制正确 |
| 合同/迁移测试 | 新旧数据库升级、Message/Event、Adapter | 跨模块合同与兼容性 |
| 集成测试 | API -> Orchestrator -> Agent -> Tool -> Artifact -> Delivery | fixture 纵向链路成立 |
| 故障回放 | 重复消息、revision 冲突、SSE 断线、服务重启 | 可恢复且不重复副作用 |
| 浏览器测试 | Workbench 桌面/移动状态和结果 | 用户可见交付可用 |
| 全量回归 | 当前测试集与 offline smoke | 已有能力未发生已知回归 |

### 10.2 必跑命令

## 11. 风险、停止条件与回滚

### 11.1 主要风险

| 风险 | 早期信号 | 处理 |
|---|---|---|
| 合同过度设计 | 字段无 fixture 或兼容路径消费者 | 删除未使用字段，推迟到 S1 |
| 双状态源 | Agent/前端状态与 Run 状态不一致 | Run/Step 保持权威，消息只作命令和投影 |
| VFS 与 Artifact 语义混乱 | 可变文件被当作不可变证据引用 | 强制显式 publish，分开 WorkspaceRef/ArtifactRef |
| 迁移破坏旧库 | 旧数据库无法打开或 checksum 变化 | 仅追加 migration，增加旧库升级 fixture |
| 兼容 Adapter 泄漏论文字段 | 通用 Server/Port 出现 `max_results` 等字段 | 将转换限制在 Adapter 内 |
| fixture 被误报为真实 Agent 能力 | 交付没有 validation-only 边界 | UI、Artifact 和测试明确 `fixture/offline` |

### 11.2 停止条件

出现以下情况时暂停当前子阶段并报告，不自动扩大范围：

1. 需要破坏性修改已有 SQLite migration 或历史 Artifact 才能继续。
2. 必须重写 `DurablePaperDiscoveryRuntime` 才能建立通用 Port。
3. 新合同依赖 FastAPI、LangGraph、Provider SDK 或具体数据库类型。
4. 全量回归出现与当前改动相关且无法在本子阶段解释的失败。
5. 实现开始需要 Dense Retrieval、真实模型、MCP、Memory 或并行 Agent 才能通过 fixture。
6. Workbench 改动演变为前端框架迁移或页面体系重做。

### 11.3 回滚

- 每个 S0.x 使用独立提交，上一验收点始终可检出运行。
- SQLite 只追加表；代码回滚后旧 Runtime 忽略新表，不执行 destructive down migration。
- 现有 `/api/v1/tasks/research` 和论文 Runtime 保留，通过 composition root 选择兼容 Adapter；Adapter 失败时可以回到原 Runtime 装配。
- Workspace 写入只发生在新的根目录；回滚不删除用户文件或 Artifact。
- fixture 和新入口在 S0.5 验收前不替换已有默认用户路径。

## 12. S0 完成定义与 S1 入口

S0 只有同时满足以下条件才可标记为 `implemented_and_validated_offline`：

1. 第 5 节最小合同实际被纵向 fixture 使用，不存在空壳 Profile 或工具。
2. Workspace URI、权限、原子写、revision 和 Artifact 发布通过安全测试。
3. Agent Message 可持久化、幂等、查询和重放，并与 Run Event 保持一致。
4. Server 依赖通用 Orchestrator Port，现有论文 API 经 Adapter 保持兼容。
5. Workbench 可完成并重新打开 fixture Run，展示结果、失败和等待输入状态。
6. 重启、重复消息、SSE 重连和冲突写入不会造成重复副作用或静默覆盖。
7. 全量测试、offline smoke 和构建通过；fixture 外部调用为 0。
8. 状态文档只记录实际结果，明确 S0 未证明真实论文检索、RAG 效果或多 Agent 协调能力。

S1 的进入条件是 S0 完成且合同没有为 fixture 之外的未来需求过度扩展。S1 首个真实目标为：

```text
自然语言论文需求
-> ResearchAgent
-> 真实论文来源与本地知识
-> 可评估的 BM25 + Dense Hybrid Retrieval
-> 证据覆盖与 Citation 验证
-> Markdown 研究结果
-> Workbench 可继续追问和修订
```

S1 才开始使用 qwen3.7flash，并建立小型真实评估集、无答案案例、token/延迟基线与引用正确性检查。只有当研究与验证角色确实需要独立上下文、工具和并行执行时，才加入第二个 Agent 和 Manager 的模型规划；不以“多 Agent 数量”作为完成指标。
