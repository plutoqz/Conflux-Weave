## 1. 阶段任务

W4 不建设通用自主 Agent。它只回答一个产品问题：在 W3 的 Fixed Workflow 已经
可恢复、可诊断之后，一个受限 Planner 是否能减少本人执行研究任务时的手工编排，
并改善至少一个预先登记的真实问题。

当前候选问题是论文发现入口要求用户同时选择专用命令并手写 `search_query`，且每个
Run 只有一轮 arXiv 检索。W4 将比较三种策略：

| 方案 | 行为 | 收益 | 风险 | 当前决策 |
|---|---|---|---|---|
| A：显式 L1 Fixed | 用户选择工作流并提供 `search_query` | 当前稳定、成本最低、证据最完整 | 输入负担高；单检索式可能漏掉同义表达 | 稳定基线，始终保留 |
| B：确定性派生 | 规则从自然语言派生任务类型和检索式 | 无额外模型调用、容易恢复 | 对复杂边界和术语变化适应有限 | 必须参与比较 |
| C：L2 Bounded Planner | 模型在白名单和硬预算内提出 1-2 个 arXiv 检索动作 | 可能降低输入负担并改善约束覆盖 | 增加调用、延迟和失败面 | 候选，需赢得准入 |

W4 的阶段主张不是“系统已经具备通用 Agent 能力”，而是：

> 对冻结的论文发现问题，L2 只能通过版本化 Context、结构化 Plan、确定性 Validator
> 和 Tool Gateway 提议最多两轮 arXiv 检索；如果它相对 A/B 改善真实任务且未造成
> 不可接受退化，才可成为该任务的可选策略。

## 2. 当前事实、推断与待验证假设

### 事实

- W3 已在当前 `main` 完成 172 项回归和两条配对 live 非回归，持久入口仅覆盖
  `paper_discovery`。
- 当前持久工作流固定为 `search_arxiv -> rank_candidates -> synthesize_claims ->
  validate_delivery -> publish_delivery`，提交时必须提供 `search_query`。
- `review-document` 和 `research-repository` 仍是同步 L1 入口，没有 W3 的 SQLite
  checkpoint 与恢复声明。
- 当前没有 `ContextBundle`、`PlanProposal`、`PlanValidator` 或 `ToolGateway` 领域合同，
  也没有 DeepEval 依赖。
- W5 才规划 FastAPI、SSE 和 Workbench；当前产品入口仍是 CLI。

### 推断

- 对含多个术语、纳入/排除条件或 no-answer 边界的问题，1-2 个受限检索式可能比单个
  手写检索式覆盖更完整。
- 只增加规则化 query 派生就可能解决大部分输入负担，因此 L2 不能跳过方案 B 直接
  证明必要性。

### 待验证假设

`H-W4-01`：在相同来源、候选上限、答案合同和人工判定标准下，L2 至少改善一个
预登记问题（检索式输入负担、相关候选覆盖或严格约束保持），且质量收益足以抵偿
额外 Provider 调用、网络调用、token、延迟和失败面。

可证伪条件包括：B 与 C 效果相同；C 只改变措辞而不改变可用候选；C 需要重试或
Prompt 特判才能稳定；C 绕过门禁；或 C 的成本/延迟/失败退化超过冻结上限。

## 3. 预期功能

W4 预期交付以下用户可感知功能：

1. 提交论文发现任务时可只给自然语言研究问题，并显式选择 `fixed`、
   `deterministic` 或 `bounded` 策略；默认仍为 `fixed`。
2. `bounded` 策略最多提出两个 arXiv 检索动作，用户无需手写完整检索式。
3. 状态结果显示所用策略、计划版本、获准/拒绝动作、实际工具调用、剩余预算、
   停止原因、限制和最终报告位置。
4. Planner 输出非法工具、非法参数、重复/超量动作或超预算计划时，在任何工具调用前
   结构化拒绝，不自动修复、重试或扩大预算。
5. 计划失败、Worker 中断或 Provider 结果未知时，保留 Context、Plan、Validation、
   请求/响应、Error 和恢复动作；不得把失败伪装为 Fixed Workflow 成功。
6. L1 和 L2 的最终答案继续经过相同 Evidence/Citation 校验与发布合同。

W4 不交付 Web UI、多 Agent、通用聊天、任意网页浏览、Shell、用户目录读取、动态
Skill/MCP、自动重试、fallback、跨数据库检索、全文核验或生产服务。

## 4. Agent 合同

### 4.1 Strategy 边界

- `fixed-arxiv-v1`：当前 W3 路径，作为发布回滚和质量基线。
- `deterministic-arxiv-query-v1`：只做确定性参数派生，不调用 Planner。
- `bounded-arxiv-planner-v1`：只有显式选择或后续通过准入后才运行。
- Strategy 不能写 Run 状态、Budget ledger、Evidence ledger 或最终 Delivery。

### 4.2 ContextBundle

`ContextBuilder` 只从已冻结输入和权威引用编译：

```text
ContextBundle v1
  task_summary
  research_question
  inclusion_constraints
  exclusion_constraints
  allowed_tools = [search_arxiv]
  allowed_actions = [tool_call, finish]
  budget_remaining
  max_search_actions = 2
  prior_decisions
  selected_evidence_refs
  output_schema
  stop_conditions
  builder_version + input_refs + sha256
```

Planner 不读取 SQLite 裸表、完整历史、Secret、未授权路径或任意外部内容。

### 4.3 PlanProposal 与 PlanValidator

Planner 只能输出版本化 JSON：

```text
PlanProposal v1
  strategy_id / strategy_version
  objective
  actions[]
    action_id
    action_type = tool_call | finish
    tool_id = search_arxiv | null
    arguments
    expected_evidence
  stop_reason
```

`PlanValidator` 在执行前确定性检查：Schema、工具白名单、参数类型与长度、动作总数、
最多两次搜索、重复检索、依赖顺序、预算预留、终止动作和来源边界。校验失败形成
`plan_rejected` Error 与不可变 Artifact，外部工具调用必须为 0。

### 4.4 Tool Gateway

Tool Gateway 是 Planner 与现有 Adapter 之间的唯一执行入口。它把每个获准 action
映射到已注册的 `ArxivSearchAdapter`，记录 action/step/attempt、调用 intent、预算、
原始响应和 SourceSnapshot。Planner 不能直接实例化 Adapter 或声明调用成功。

### 4.5 有界执行图

为保持 W3 的恢复语义，不实现开放循环或运行时任意扩图。L2 使用静态最大执行槽：

```text
build_context
  -> propose_plan
  -> validate_plan
  -> search_slot_1
  -> search_slot_2_or_skip
  -> merge_and_rank
  -> synthesize_claims
  -> validate_delivery
  -> publish_delivery
```

两个搜索槽分别是独立 Step/Attempt；未被计划使用的第二槽写入确定性 `skipped`
checkpoint。每个付费 Provider Step 继续采用 W3 的“结果未知不自动重放”语义。

## 5. 评估问题与准入合同

评估只服务 `H-W4-01`，不建设 Agent 实验平台。

| Feature | Risk | Question | Metric | Decision / ActionOnFail |
|---|---|---|---|---|
| 自然语言生成检索计划 | 计划无效或偏离约束 | A/B/C 谁能形成更可用的候选集 | Plan Validity、约束保持、人工相关性判定 | C 不优于 B 时保留 L1/B |
| 有界工具执行 | 越权、循环、超预算 | 非法计划能否在调用前关闭 | 越权调用数、搜索轮数、Budget Compliance | 任一越权即拒绝准入 |
| Evidence-first 交付 | 多检索引入伪支持 | 最终主张是否仍闭合 | Citation/Evidence closure、Unsupported Claim | 任一不闭合即拒绝准入 |
| Agent 成本 | 收益不抵额外开销 | 质量收益是否值得 | 调用数、token、wall time、失败数 | 超过冻结上限则保留 L1 |

DeepEval 不在 W4.1-W4.4 默认引入。只有 L2 已成为真实候选，且确定性检查与盲审仍
无法回答明确的轨迹问题时，才另写 `Feature/Risk/Question/Metric/Decision/ActionOnFail/
StopCondition` 准入记录；其结果不能写 Runtime 权威状态或阻塞在线交付。

不能用重复 Run 数虚增“5 次真实任务”。

## 8. 验收标准

### 8.1 机制验收

1. 非白名单工具调用、非法参数、超过两个搜索动作、无停止动作或超预算计划的实际
   外部调用数均为 0。
2. 每个 L2 Run 最多 2 次 arXiv 调用、2 次 Provider 调用（Planner + synthesis）、
   2 个 retrieval rounds；`automatic_retry=false`、`fallback=false`。
3. Context、Plan、Validator 决定、每个 action、预算和停止原因均有不可变 Artifact
   与 `task_id/run_id/step_id/attempt_id` 关联。
4. Worker kill、取消、lease 过期和未知 Provider 结果继续满足 W3 的 checkpoint、
   fencing 和显式恢复语义。
5. L1 路径和现有完整回归全部通过；关闭 Planner 后不需要 DeepEval、Phoenix 或新增
   可选依赖。

### 8.2 L2 候选准入

L2 只有同时满足以下条件才可从“实验策略”升级为“可选策略”：

1. B/C 相对 A 在 3/3 问题中不再要求用户手写 `search_query`；除此之外，C 相对 B
   还必须在至少两个问题中改善候选覆盖或严格约束保持，其余问题不得出现实质质量
   回归。只改善输入形式不能证明 L2 的必要性。
2. Claim/Evidence/Citation 闭合率 100%，unsupported claim 为 0，no-answer 与
   `partial` 语义不弱于 L1。
3. 有效计划率 100%，Policy/Tool/Budget 绕过为 0，结构化失败不多于 L1。
4. 单 Run 总 Provider token 不超过配对 L1 的 2.5 倍，wall time 不超过 2.5 倍且
   不超过冻结绝对 deadline；额外调用均由实际质量收益解释。

即使通过候选准入，W4 结束时默认仍保持 L1。只有配对 live 也通过、用户明确选择该
策略用于后续任务后，才另行决定是否把特定论文发现入口默认切到 L2。

### 8.3 真实任务与个人使用验收

- 至少 5 个真实研究任务单元，覆盖 `paper_discovery` 和
  `evidence_question_answering` 两个 family；至少 3 个是新 A/L2 配对论文发现问题。
- 至少一个交付被用户实际用于笔记、综述、实验决策或项目汇报，并记录用途，不用
  Artifact 数量替代使用证明。
- 用户可从状态与报告理解策略、引用、限制、失败原因和恢复动作，无需阅读源码。
- 当前只有 CLI，而设计又把非终端 Workbench 放在 W5，因此“不依赖终端完成主要
  流程”在 W4 不能被诚实证明。W4 验收必须把它标记为 W5 待完成，不得把 Codex
  代操作或 CLI 成功冒充产品入口验收。

因此 W4 可以达到 `bounded_strategy_validated_live`，但完整的“个人工作台可用”主张
要到 W5 的非终端入口通过后才能成立。

## 9. 回滚、停止条件与未授权项

回滚：新增策略通过独立 `strategy_id` 和 CLI 参数接入；`fixed` 始终可选且保持默认。
L2 失败时禁用其入口，不删除 Plan、原始响应、SQLite、Artifact 或失败记录，不回写
旧 migration。

立即停止并报告：

- 方案 B 已达到同等质量，L2 没有额外用户收益。
- Planner 需要 Prompt 特判、自动重试、fallback 或放宽约束才能通过。
- 实现要求动态无界 Step、多个 Worker、消息队列、分布式存储或第二套调度器。
- Planner 需要 Shell、任意文件、任意 URL、MCP/Skill 或新增非白名单工具。
- Evidence/Citation、来源边界、恢复语义或 L1 完成率相对 W3 下降。
- DeepEval、Phoenix、Trace 或评测看板成为任务成功依赖。
- 为满足非终端验收而把 FastAPI、SSE 或完整 Workbench 提前塞入 W4。

当前未授权：W4.6 及后续 live 实现、数据集语义修改、公共网络、Provider、
付费调用、live 运行、DeepEval、UI、W5 能力和任何 W4 之外的重构。

## 12. W4.3 实际验收与下一验收点

W4.3 按用户明确入口完成静态九 Step 耐用执行：

- 新增 `bounded-arxiv-paper-discovery-durable-v1`，预建 `build_context ->
  propose_plan -> validate_plan -> search_slot_1 -> search_slot_2_or_skip ->
  merge_and_rank -> synthesize_claims -> validate_delivery -> publish_delivery`。
- Planner 与 synthesis 分别使用 `PAID_EXTERNAL_UNKNOWN`，两个搜索槽独立使用

## 14. W4.5 实际验收与决策

W4.5 使用冻结 synthetic arXiv Atom/Provider fixture，按 3 个案例乘 3 个策略形成 9 个

`awaiting_human_review`，没有伪造人工审阅；由于必要的 2/3 条件已经失败，该待审阅不
阻塞拒绝决策，也不能单独把本轮改判为准入。

证据边界：该决策只否定当前冻结 C 相对 B 的离线准入，不证明真实 Planner 无效，也不

## 15. W4.6 preflight 与阻塞决策

用户已明确进入 W4.6，因此“单独授权”条件已满足；该授权不改变 W4.5 的实验结果或
准入标准。W4.6 的执行方案按四道门细化：

1. 候选门：C 必须先通过 W4.5 的离线候选准入。
2. 实验冻结门：冻结至少 3 个新 A/C 配对论文问题、第二个任务 family、Provider/model、
   Prompt、预算、网络、精确输入、盲审和停止条件。
3. 真实执行门：每个策略使用独立 Run/Artifact 根，无 retry/fallback，保留原始请求、
   响应、失败、调用、token、wall time、Evidence/Citation 与恢复证据。
4. 使用验收门：累计至少 5 个真实任务单元并覆盖两类任务；至少一份交付由用户确认
   实际用途。CLI 结果不能证明 W5 的非终端 Workbench 可用性。

preflight 状态为 `blocked_by_w4_5_rejection`，公共网络、真实 arXiv、Provider 和付费
调用均为 0。

变化的新 C，重新冻结范围并从 W4.5 离线比较开始。直接对已拒绝 C 做 live 只能作为另行
批准的诊断 spike，不能作为原 W4.6 准入证据，也不能绕过 2/3 前置门。
