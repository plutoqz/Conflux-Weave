## 1. 转段结论与事实边界

W4 已经得到一个有效的负向产品决策，而不是 Agent 准入成功：

- `bounded-arxiv-planner-v1` 在冻结离线 A/B/C 中只改善 1/3 案例，未达到 2/3 门槛，机械决策为 `reject`。
- W4.6 因候选门失败停在 preflight，真实 arXiv、Provider、付费调用和 live Run 均为 0。
- `fixed-arxiv-v1` 继续作为默认稳定策略；已拒绝 Planner 的代码和证据保持可读，但不进入 W5 用户入口。
- W4 原计划中的五次真实任务、两类任务和个人使用审计尚未在 W4.6 完成。这是 W5 发布门的前置债务，不能改写为已通过。
- 当前 W4 修改仍位于未提交工作树。W5 实现必须先冻结精确源码和差异，不能直接把 `HEAD=01ffc319` 当作完整 W4 基线。

因此，进入 W5 的含义是：接受 W4 的负向决策，停止扩展当前 Planner，围绕已经通过离线与配对 live 验证的 Fixed Workflow 建设可使用、可恢复、可安装的产品入口。

## 2. W5 目标、主张与成功条件

### 2.1 阶段目标

交付一个本地优先、单服务的最小 Research Agent Workbench，使本人和不了解内部架构的新用户能够：

```text
Fresh Clone -> Install -> Configure One Provider -> Start
    -> Ask First Question -> Observe Progress -> Cited Answer
    -> Inspect Evidence / Limitations -> Reopen Or Recover Run
```

首版黄金路径只承接 W3 已验证的耐用论文发现 Fixed Workflow。W1/W2 的其他一次性能力不因为存在 CLI 就自动获得 Workbench、恢复或发布级能力。

### 2.2 可证伪主张

`H-W5-01`：在不引入第二套状态、调度或前端服务的前提下，单 FastAPI 应用、SQLite 权威状态、一个 Worker 和最小 Web Workbench 可以让新用户在清洁环境中 10 分钟内完成首次带引用查询，并让本人无需源码或终端持续查看、取消、恢复和复用历史 Run。

以下任一情况会否定阶段完成：

1. 首次查询仍要求用户理解 Runtime、Step、Artifact 或内部数据库。
2. UI 只能启动任务，刷新、断线、取消、失败或重启后无法继续处理。
3. Citation 不能从回答反向打开 Evidence 和 SourceSnapshot。
4. 清洁环境路径超过 10 分钟，或依赖本机已有缓存、私有文件和 Codex 代操作。
5. 默认安装依赖 Phoenix、Ragas、DeepEval、LangGraph、Node.js 或外部 Trace 服务。
6. 测试、HTTP 200、SSE 连通或页面截图通过，但真实用户任务未形成可用交付。

### 2.3 阶段完成定义

W5 只有同时满足以下五层才可标记 `completed`：

1. 用户任务完成：可提交、等待、取消、恢复、查看和重新打开黄金路径 Run。
2. 交付可用：回答、引用、Evidence、限制、未满足条件和恢复动作清晰可读。
3. 稳定恢复：刷新、SSE 断线、服务重启和显式恢复不破坏 SQLite 权威状态。
4. 首次成功：独立清洁环境从 clone 到首个带引用答案不超过 10 分钟，Provider 等待时间单列。
5. 真实使用：累计至少 5 个真实任务单元、覆盖 2 个既有任务 family，且至少 1 份交付由用户确认用于笔记、综述、实验或项目判断；其中至少 2 次通过 Workbench 黄金路径完成。

第五层可以复核 W1-W3 已保留的合格真实 Run，但不得重复计数 A/B/C 策略 Run、失败重跑或 Codex 演示；既有证据不足时必须补做新的 Fixed 真实任务。第二个 family 只用于个人使用审计，不在 W5 中扩建成第二条耐用 Workbench 垂直切片。

## 3. 技术方案比较与选择

### 3.1 方案 A：FastAPI + 包内静态 HTML/CSS/ES Modules

收益：

- 与 Python 包、单端口和 `uv` 安装路径一致，不要求新用户安装 Node.js。
- 可由 FastAPI 同源提供页面、API 和 SSE，最容易满足 10 分钟首次成功。
- 首版交互面较小，使用原生 Web API 足以实现 Run 列表、状态投影、取消和恢复。

局限：

- 需要自行维护少量状态管理、可访问性和前端测试。
- 若 W6 以后页面显著扩展，可能需要重新评估组件化前端。

### 3.2 方案 B：FastAPI + React/Vite 构建产物

收益：成熟的组件、路由和测试生态，后续复杂交互更易组织。

局限：增加 Node.js、lockfile、构建、依赖审计和发布链路；当前一个黄金路径不足以证明这些复杂度有必要，并直接增加 fresh clone 成本。

### 3.3 方案 C：Streamlit、Gradio 或第二个前端服务

收益：原型速度快。

局限：容易形成第二套服务入口和状态语义，SSE cursor、历史 Run、显式恢复、细粒度可访问性和统一 OpenAPI 均不自然，不符合冻结复杂度预算。

### 3.4 决策

W5 采用方案 A。FastAPI 和 Uvicorn 是设计已接受但尚未落地的生产依赖；接受依赖前补一条 ADR。前端保持包内静态资源，不使用 CDN，不要求 Node.js，不建立组件库、营销页或前端插件体系。

## 4. 冻结产品功能面

### 4.1 首屏工作台

首屏直接进入研究任务，不设置 landing page：

- 查询输入、普通研究语言的检索条件和提交命令。
- 当前 Run 的用户语言状态、紧凑进度、预算摘要和取消动作。
- 回答正文与数字引用；引用可打开对应 Evidence 和 SourceSnapshot 定位。
- 可展开限制、未满足条件、恢复动作和技术详情。
- 历史 Run 列表，可按最近时间重新打开。

Workbench 不显示内部 Agent 数量、LangGraph node、评测分数、Trace 面板或 SQLite 状态名。`fixed-arxiv-v1` 是唯一可提交策略；被拒绝的 bounded 策略不出现在产品模式选择中。

### 4.2 首版 API

API 使用版本前缀 `/api/v1`，错误统一映射为稳定 JSON 合同：

```text
POST   /api/v1/tasks/research
GET    /api/v1/runs?cursor=&limit=
GET    /api/v1/runs/{run_id}
POST   /api/v1/runs/{run_id}/cancel
POST   /api/v1/runs/{run_id}/resume
GET    /api/v1/runs/{run_id}/events?after={event_id}
GET    /api/v1/runs/{run_id}/artifacts
GET    /api/v1/evidence/{evidence_id}
GET    /api/v1/health/live
GET    /api/v1/health/ready
```

合同约束：

- POST 只创建或返回同一幂等 Task/Run，不在请求线程内执行完整研究流程。
- SSE 只投影 SQLite `run_events`；`event_id` 是 cursor，断线续读按 ID 去重。
- Run 快照是终态权威；客户端不得把最后一条 SSE 当作终态。
- `resume` 只接受 Runtime 已允许的显式恢复决定。未知付费调用不自动重放。
- 取消后不再启动新外部调用；终态取消是幂等响应。
- Artifact/Evidence 读取只允许数据库登记引用，不接受任意文件路径。
- HTTP 错误不直接暴露内部异常、API Key、Provider 原始响应或本地绝对路径。

### 4.3 单命令运行边界

新增一个面向用户的启动命令，启动单 Uvicorn 进程和一个应用内 Worker 循环：

```text
conflux-weave serve
```

ASGI lifespan 负责 Worker 启停；SQLite lease/fencing 继续承担权威并发控制。首版明确禁止多 Uvicorn worker，服务重启后按 W3 恢复合同继续。CLI durable 命令保留为开发和恢复入口，但不是黄金路径依赖。

### 4.4 配置、隐私和离线 smoke

- Provider 仍只从环境或忽略的 `.env` 读取；浏览器不提供保存 API Key 的后端接口。
- 就绪检查只验证字段、数据库、Artifact 目录和 schema，不为 readiness 发起付费或公网调用。
- 缺少配置时在提交前阻止任务，展示缺失字段和修复动作，不回显 Secret。
- 提供版本化最小示例语料和 `offline smoke`。它使用固定本地输入和 fixture Adapter，清楚标记 `offline_smoke`，验证安装、API、Run、Delivery、Citation 和 UI 读取，不声明 live 能力。
- 默认数据写入 `var/` 或用户指定数据根；日志、数据库、Artifact、研究输入和 Secret 均受忽略与 secret-scan 检查。

- 不把 README、截图、测试数或 HTTP 成功当作真实用户能力证据。

## 9. 回滚与停止条件

回滚：FastAPI/Workbench 只调用既有 Application/Runtime 合同；CLI 与 `fixed-arxiv-v1` 保持可独立使用。新增 SQLite 能力采用向前 migration；回滚应用版本时保留数据库和 Artifact，不删除历史 Run。

立即停止并报告：

- Workbench 迫使修改 Evidence、Budget、Lease/Fencing 或未知外部结果的权威语义。
- 单命令启动必须依赖第二套调度器、第二个服务、多 Worker 或 Node 构建环境。
- 首次成功必须把 Secret 写入仓库、数据库、URL、浏览器存储或 Artifact。
- UI 只能通过轮询内存状态工作，无法从 SQLite 恢复。
- 为满足 10 分钟目标而跳过引用闭合、错误保留、真实安装或真实 Provider 路径。
- W5 实际要求迁移第二个垂直切片，导致目标、工期或验收标准发生变化。

Pydantic 2.13.4 和 Uvicorn 0.52.4。首次 `uv lock --offline` 因所需包体不在本地缓存而
失败并保留；随后正常依赖解析访问了包注册表。这只是依赖获取，不是研究网络或 live
能力证据。

实现新增冻结 Pydantic 请求/响应模型、用户态 Run 投影、脱敏异常映射、结构化不透明
Run cursor，以及只读 `WorkbenchQueryService`。SQLite Repository 新增稳定的
`(created_at, run_id)` 降序分页、`event_id` 续读、Run Event 对象校验和 Artifact
注册查询。Delivery Artifact 只能通过当前 Run 的 Delivery 注册关系读取；Evidence
先验证 Delivery 引用，再只解析当前 Run 成功 rank Step 的已注册 checkpoint，缺失、
损坏或冲突定义均 fail closed。readiness 只检查本地数据库、Artifact 根和配置布尔值，
不回显路径或 Secret，也不发起 Provider 调用。

聚焦合同和架构测试通过 24 项，完整离线回归通过 249 项；compileall、lock check 和
离线 sdist/wheel 构建通过。W5.1 没有创建 FastAPI app、启动 Uvicorn/Worker、实现 SSE
transport 或 Workbench，也没有浏览器、研究来源、Provider、付费调用或 live Run。
详细命令、失败保留、包版本和构建 hash 见 W5.1 验收 JSON。

本验收证明应用查询与 API 数据合同的离线机制，不证明 HTTP 路由、后台执行、断线 SSE、
Workbench 可用性、清洁环境首次成功或任何新的 live 研究能力。

## 13. W5.2 实际验收

W5.2 在同一未提交 W5 工作树上实现唯一 FastAPI ASGI 边界。`create_app` 通过 lifespan
启停一个注入的 `WorkerLoop`；`build_local_app` 组装现有 SQLite Repository、Artifact
Store、应用服务和 Worker。CLI 新增显式 `serve` 命令，并固定 Uvicorn `workers=1`，
没有引入第二个调度器、服务边界或内存权威状态。

HTTP 路由覆盖 research task 提交、Run 列表与详情、取消、显式恢复、Event SSE、
Artifact、Evidence 和本地健康检查。提交、取消和恢复均写回 SQLite；SSE 只投影持久化
`run_events`，按 `event_id` 续读并在 Run 终态后结束。Provider 配置缺失时 readiness
本地降级，不发起外部调用。W5.2 没有提供 Workbench 页面或静态资源。

聚焦服务、合同、架构与范围测试通过 30 项，完整离线回归通过 255 项；compileall 和
模块导入通过。验收期间没有启动 Uvicorn 进程；仅 lifespan fixture 启停一个注入 Worker。
浏览器、研究来源、Provider、付费调用和 live Run 均为 0。

本验收证明单进程离线 HTTP/Worker/SSE 机制，不证明真实 socket 服务、跨进程部署、
Workbench 可用性、真实 Provider 执行、清洁环境首次成功或生产可靠性。

## 14. W5.3 实际验收

W5.3 在 W5.2 单 FastAPI 边界内增加打包的同源 HTML、CSS 和 ES Module Workbench，
没有 Node 构建、CDN、前端框架或第二个服务。首页提供研究提交、近期 Run、用户态状态、
进度和预算摘要、取消、两种显式恢复决定、Delivery 回答、Evidence、限制、未满足标准、
恢复动作和持久化 SSE 动态。刷新后所有主视图均从 SQLite/API 重建，浏览器不保存 Secret。

为展示回答，服务增加受控 Delivery Artifact 文本读取路由：先验证 Artifact 属于指定 Run
已发布的 Delivery，再校验内容 hash、2 MB 显示上限和 UTF-8；未登记 Artifact 返回 404，
不接受文件路径。Windows 首次将 `.js` 返回为 `text/plain`，浏览器按模块 MIME 规则拒绝
执行；修复为显式注册 `text/javascript`，并为打包资源增加版本查询参数避免旧错误缓存。

首次测试方案使用 Starlette `TestClient`，因当前环境缺少其新要求的 `httpx2` 在收集阶段
失败；未增加依赖，改为沿用现有 ASGI 端点直调合同测试，并由真实本地 Uvicorn fixture
覆盖 HTTP/浏览器层。聚焦测试通过 32 项，完整离线回归通过 257 项；compileall、JS
syntax 和 `git diff --check` 通过。

浏览器 fixture 在 1440x900 和 390x844 视口验证预置回答、两条 Evidence、证据详情、
限制与恢复动作、创建、取消和刷新恢复。移动视口无横向溢出，对话框完整落在可视宽度内，
控制台无 error/warn。验收启动两个先后替换的 fixture Uvicorn/Worker（首次用于发现 MIME
问题），均使用隔离数据根；研究来源、真实 Provider、付费调用和 live Run 为 0。

本验收证明离线 fixture 下的最小 Workbench 机制和响应式可用性，不证明安装包资源完整、
离线 smoke、清洁环境首次成功、真实研究能力、真实 Provider 路径或生产可靠性。
