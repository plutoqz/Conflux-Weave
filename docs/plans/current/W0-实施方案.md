## 1. 目标与交付边界

W0 冻结首版用户问题、数据边界、核心合同和依赖方向，形成可进入 W1
的最小验证性骨架。它不交付 Research Query 产品链路，也不把测试通过、
包构建成功或目录存在解释为 Agent/RAG 真实能力。

本阶段交付：

1. 独立的 `conflux-weave` 包、Git 仓库和本地数据根。
2. Task/Run/Step、Budget、Error、Artifact/Evidence/Claim/Citation 合同草案。
3. 不依赖旧 Conflux 和外部框架的自动边界检查。
4. 10 至 15 个代表用户案例，覆盖论文发现、证据问答、无答案和来源失败。
5. 版本化数据集 Manifest、功能验收清单和旧数据只读导出清单。

明确非目标：FastAPI、Worker、SQLite schema、检索实现、模型 Provider、
Web Search、UI、LangGraph、Phoenix、Ragas、DeepEval，以及任何付费或 live
调用。上述内容分别等待 W1-W5 的真实消费者。

## 2. 已确认基线

- 初始化前目录只有设计文档，不是 Git 仓库，也没有代码或运行服务。
- 旧仓库位于 `D:\code\Conflux`，本计划不修改其代码、配置、数据库或 Git
  状态；旧仓库只作为后续只读导出盘点来源。
- Python 采用设计允许的 3.11+；本地框架验证固定为 uv 管理的 Python 3.12。
- 未获得真实 Provider、网络检索、付费评测或旧数据迁移授权。

## 3. 数据存放与生命周期

| 数据类别 | 存放位置 | Git | 规则 |
|---|---|---|---|
| 小型冻结案例 | `datasets/<layer>/<dataset-id>/` | 提交 | 必须有 Manifest、稳定 case ID、hash 和标注规则 |
| 本地权威状态 | `var/db/` | 忽略 | W3 前不实现数据库；不得用 YAML 双写权威状态 |
| Source/Artifact | `var/artifacts/sha256/` | 忽略 | 内容寻址、不可原位覆盖；W1/W3 实现时验证 |
| FTS/向量索引 | `var/indexes/` | 忽略 | 只允许由 Source Snapshot 重建 |
| 旧数据迁移暂存 | `var/imports/` | 忽略 | `export -> validate -> normalize -> import manifest` |
| 评测原始结果 | `var/evaluations/` | 忽略 | 保存失败和原始响应，不回写 Runtime 状态 |
| 对外交付 | `var/exports/` | 忽略 | 显式导出，不作为仓库文档 |

W0 只提交无敏感信息、可人工审阅的小型案例。真实论文全文、用户项目材料、
API 响应、Secret、SQLite、索引和生成报告不得进入 Git。若案例需要受限原文，
Manifest 只记录稳定外部引用和 hash，不复制未授权内容。

## 4. 文档管理

- `docs/design/current/` 是当前设计依据；新版本进入 current 后，旧版本原样
  移入 `docs/design/archive/`。
- `docs/plans/current/` 只保存正在执行的计划；归档前记录实际结果、失败、
  未验证项和后继计划。
- `docs/decisions/` 只保存已接受 ADR。新增核心依赖或概念时说明真实用户问题、
  现有能力不足、黄金路径失败影响、回滚方式和真实消费者。
- `docs/status/project-status.md` 是能力状态入口，但不替代测试输出或运行产物。
- Trace、评测报告和 Provider 原始响应属于 `var/` Artifact，不进入 docs。

## 5. 工作包与顺序

### W0.1 仓库和骨架

范围：初始化 Git、uv、`src/` layout、最小合同模块、测试入口、`datasets/`
与 `var/` 边界。

验收：`uv sync --frozen`、`uv run pytest`、`uv build` 通过；生成的 wheel 仅含
`conflux_weave` 新包。

### W0.2 用户任务冻结

先定义案例 schema，再与用户冻结 10 至 15 个案例。建议组成：

- 4 至 5 个论文发现案例。
- 4 至 5 个论文/项目证据问答案例。
- 2 至 3 个无答案、冲突或证据不足案例。
- 1 至 2 个来源不可达、格式不支持或权限受限案例。

每个案例必须记录：

```text
case_id, task_kind, input, deliverable, required_evidence,
allowed_confirmation, acceptable_degradation, completion_criteria,
source_policy, sensitivity, annotation_status
```

指标只有在关联 `Feature / Risk / Question / Decision / ActionOnFail /
StopCondition` 后才能加入 Manifest。

### W0.3 合同和边界冻结

逐项核对合同字段、枚举和失败语义。合同仍可修改，但每次修改必须由 W0 案例或
W1 最小消费者触发。加入依赖检查：

- 新包不 import `conflux`。
- Core 不 import FastAPI、Provider SDK、LangGraph、Trace 或 Eval 框架。
- Evidence 不依赖 UI 或 Provider SDK。

### W0.4 旧数据只读盘点

只读取旧仓库，生成导出清单，至少包含：路径/数据集 ID、用途、schema/version、
大小/记录数、敏感级别、权威性、历史评测边界、建议动作和 hash 方法。首版只将
评测集与测试语料列为迁移候选；历史 Run 默认静态归档，不伪装为 Weave Trace。

### W0.5 离线验收

运行边界测试、合同测试、包构建和 Manifest 校验，检查 Git 差异中不存在 Secret、
数据库、索引、原始 Provider 响应或用户私有材料。将实际命令、revision、Python
版本、case 数和 hash 写入 W0 验收记录。

## 6. 验收标准与证据

| 验收项 | 通过条件 | 证据 |
|---|---|---|
| 独立性 | 新包无旧 Conflux import | AST 依赖测试输出 |
| 框架隔离 | Core/Evidence 无禁用框架依赖 | AST 依赖测试输出 |
| 数据版本化 | 冻结案例有 schema、Manifest、hash | 数据集文件与校验输出 |
| 用户价值先行 | 每个案例先定义交付和完成判定 | 人工复核后的 cases.jsonl |
| 历史边界 | 旧资产有来源和建议动作，未直接迁移 | 只读导出清单 |
| 可复现性 | 冻结环境可测试和构建 | `uv.lock`、命令输出、Git revision |

W0 只有全部验收项通过后才能标记 `validated_offline`。没有真实 Provider、真实网络、
真实研究流程，所以本阶段不能标记 `validated_live` 或 `completed`。

## 7. 回滚、恢复与停止条件

回滚：W0 不修改旧仓库或外部数据。任何合同草案可通过新提交回退；数据集版本一旦
被验收引用，不原位改写，修订时创建新版本并保留旧 Manifest。

恢复：每个工作包完成后提交独立 Git revision，并在状态文档记录下一单一验收点。
中断后从最近已通过的工作包继续，不重复迁移或生成数据。

立即停止并上报：

- 启动骨架需要复制或 import 旧 Conflux 大模块。
- 核心合同连续两次因 FastAPI、LangGraph、Provider 或评测框架而改变。
- 案例无法明确用户交付、必要证据或完成判定。
- 发现必须迁移私有数据、调用真实 Provider 或改变产品目标才能继续。

W0.3 约 2 至 4 小时，W0.4 约 1 至 3 小时，W0.5 约 1 至 2 小时。

当前 W0.1-W0.5 均已达到 `validated_offline`。12 个 frozen cases 已映射到最小
Core、Evidence、确认和降级合同；旧 Conflux 资产已完成只读盘点，未执行复制或
迁移；全量离线测试、构建和敏感路径检查通过。

下一单一验收点是：**依据设计 v0.2 冻结 W1“本人可用的最小 Research Query
垂直切片”的目标、真实输入、完成判定、Provider/网络授权边界与最小验证集。未经
新的实施确认，不进入 W1 Workflow、Provider 或网络检索编码。**
