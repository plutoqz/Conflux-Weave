# Conflux-Weave v0.3 · P7 后续迭代路线与验收方案

- 日期：2026-09-13
- 性质：P6 收尾后的后续路线方案
- 前置依据：
  - `v0.3-P6-具体执行方案.md`
  - `v0.3-P6-执行记录与Gate验收.md`

## 1. 当前判断

当前系统已经达到研究型 Agent Workbench 的第一阶段成熟度：

- 研究结果可导出；
- 对话、Run、文档支持生命周期管理；
- 长任务具备阶段反馈、SSE 重放和通知；
- 记忆具备真实 embedding 召回、作用域隔离和确定性降级；
- 计算工具具备单机研究工具级沙箱；
- API 与 Worker 已能分离；
- `retrieve/deliver` 外层已经具备 checkpoint 和恢复能力。

但当前还没有达到成熟 Agent 平台的完整形态：

- C2 内部阶段尚未统一纳入 durable checkpoint；
- Provider 故障转移和结构化输出容错不足；
- MCP 和计算工具还缺少生产级治理；
- 记忆缺少完整生命周期；
- 全局搜索、PDF 研读联动和备份迁移尚未形成闭环；
- 多租户、鉴权、监控和容量模型仍未建设。

因此，当前剩余工作不能全部视为验证任务：

```text
已实现能力的真实运行确认：验证任务
未实现能力和架构短板：继续开发任务
```

## 2. 总体路线

```text
P7-V  P6 真实能力验证与状态收尾       由用户执行真实测试
P7-A  研究资料与知识组织能力           近期实现
P7-B  记忆生命周期与 Agent 反馈         中期实现
P7-C  Durable Workflow 与 Provider治理  架构升级
P7-D  工具生态与扩展能力               架构/生态升级
P7-E  市场化部署能力                   单独上线计划
```

推荐顺序：

```text
先完成真实验证
→ 再补高频用户功能
→ 再统一执行和容错模型
→ 最后进入多人和公网部署
```

## 3. P7-V：P6 真实能力验证与状态收尾

这一阶段不新增主要功能，目标是把已实现能力从“代码和离线测试成立”推进到“真实运行边界清楚”。

### V1 A5 设置与 NotePatch

#### 验证内容

- 修改 Chat、Embedding、Reranker、Engine 模型；
- 保存配置；
- 确认持久化值；
- 确认当前进程生效值；
- 重启服务；
- 确认重启后生效；
- 执行 Provider Chat + Embedding 连通性测试；
- 正常创建 NotePatch；
- 制造一次版本错配，确认 409 响应和前端提示。

#### 证据

- 配置修改前后 API 响应；
- 重启前后 `provider` 与 `provider_effective`；
- 连通性测试结果；
- NotePatch 成功和冲突结果；
- 浏览器截图或录屏；
- 服务日志中的错误和状态。

#### 通过标准

- 保存成功和失败状态明确；
- `requires_restart` 与实际行为一致；
- 重启前不会谎称新模型已经生效；
- 重启后生效值与持久值一致；
- NotePatch 正常链路不再返回 422；
- 409 不会静默覆盖用户修改。

### V2 B1 真实 embedding 召回

#### 验证内容

- 使用真实 embedding Provider；
- 执行零词法重叠配对查询；
- 执行无关查询；
- 执行跨项目查询；
- 重启服务后再次查询；
- 暂时移除 embedding 配置后验证降级；
- 记录延迟、维度、失败原因和调用次数。

#### 通过标准

- 配对查询达到既定最低命中门槛；
- 无关查询不强行注入；
- 跨项目记忆零泄漏；
- 重启后索引不重新错误建表；
- embedding 不可用时稳定回退；
- 真实 Provider 失败不会影响主对话流程。

不把一次矩阵结果升级为长期质量结论。后续仍需要更大规模记忆评估集。

### V3 C1/C2 真实恢复

#### C1 验证

- API 使用 `serve --no-worker`；
- 独立 Worker 处理任务；
- API 重启；
- Worker 重启；
- lease 过期接管；
- SSE 从数据库补发；
- 已完成步骤不重复执行。

#### C2 验证

- 在 retrieve 阶段后终止 Worker；
- 在 deliver 前终止 Worker；
- 重启 Worker；
- 确认输出 Artifact 可复用；
- 确认付费批次不重复调用；
- 确认失败记录和 checkpoint 保留。

#### 诚实边界

本阶段只能确认：

```text
外层 retrieve/deliver 恢复闭环：真实验证
内部 plan/claim/verify/synthesize/write 逐段恢复：仍未实现
```

### V4 W3 深度研究真实验收

至少执行：

- 一次正常深度研究；
- 一次部分失败或来源不可用；
- 一次长任务刷新恢复；
- 一次导出；
- 一次人工报告质量检查。

人工检查：

- 数字是否漂移；
- 引用是否支撑正文；
- 失败边界是否如实展示；
- 报告结构是否可直接用于后续论文写作；
- 研究耗时和进度反馈是否可接受。

### V5 状态收尾

完成真实验证后同步：

- `docs/status/project-status.md`；
- P6 Gate 记录；
- 真实 Run ID；
- 失败案例；
- 未验证边界；
- 实际测试数字。

禁止使用“已完成”覆盖仍未验证的真实能力。

## 4. P7-A：研究资料与知识组织能力

这是下一阶段最值得优先实现的用户功能批。

### A1 全局搜索

#### 目标

提供统一入口搜索：

- 对话；
- 研究报告；
- 笔记；
- 文档；
- 论文；
- Evidence；
- 项目文件。

#### 推荐实现

```text
结构化过滤
→ SQLite FTS/BM25
→ 可选语义召回
→ 类型/时间/项目重排
→ 原文定位跳转
```

SQLite 作为元数据和文本搜索权威；LanceDB 只承担语义候选召回，不复制对象生命周期。

#### 最小 API

```text
GET /api/v1/search?q=&types=&project_id=&from=&to=&limit=
GET /api/v1/search/{result_id}/locate
```

#### 验收标准

- 一个查询可跨多个对象类型返回结果；
- 结果带类型、标题、更新时间和匹配原因；
- 可以跳到对话消息、笔记段落、文档页码或 Evidence；
- 归档和软删除对象按筛选规则处理；
- 无结果时不调用生成模型；
- 结果不跨项目泄漏。

### A2 PDF 研读联动

#### 最小闭环

```text
打开 PDF
→ 选择文本或图表
→ 提问/生成笔记
→ 自动附带 document_id、页码、segment_id
→ 生成 NotePatch 或研究任务
→ 从笔记跳回原文定位
```

#### 验收标准

- 文本选择带页码和 segment 定位；
- 图表选择带 asset_id 和父 Chunk；
- 生成的笔记保留原始引用；
- 笔记引用可以回到 PDF；
- 无定位信息时明确标记，而不是伪造页码；
- 失败时保留用户选中的原文。

### A3 备份、恢复与迁移

#### 首批范围

- SQLite；
- LanceDB；
- Artifact Store；
- source-cache 中的必要元数据；
- 配置模板，不包含密钥明文。

#### 备份包内容

```text
backup-manifest.json
runtime.sqlite3
lancedb/
artifacts/
config-template.env
```

#### 验收标准

- 一键生成备份；
- 备份前执行数据库一致性检查；
- 恢复前验证版本和路径；
- 恢复后 SQLite、向量索引和 Artifact 数量一致；
- 随机抽样 Artifact 可读；
- 恢复失败不覆盖原数据；
- 备份结果不包含 Provider key。

### A4 研究任务组织

新增：

- 标签；
- 收藏；
- 最近访问；
- Project 下 Run 分组；
- Run 与笔记关联；
- 研究任务模板；
- “继续上次研究”入口。

第一批不引入复杂知识图谱或自动分类系统。

## 5. P7-B：记忆生命周期与 Agent 反馈

### B1 记忆治理

新增用户操作：

- 固定记忆；
- 忽略记忆；
- 标记过期；
- 合并重复记忆；
- 修改作用域；
- 查看被哪些回答使用；
- 标记“有用/无用”。

### B2 衰减与有效期

记忆排序可引入：

```text
semantic_score
+ lexical_score
+ scope_score
+ user_feedback
+ recency
- expired_penalty
- conflict_penalty
```

不要仅通过扩大 top-k 解决召回失败。

### B3 程序性记忆

只允许从满足条件的 Run 提取候选经验：

- Run 成功；
- 用户明确标记有用；
- 关键 Artifact 和 Evidence 完整；
- 经 HITL 核准；
- 保存来源 Run ID。

不自动把所有历史 Run 转成长期记忆。

### B4 记忆评估

建立小型真实评估集，包含：

- 偏好；
- 项目背景；
- 同义表达；
- 冲突；
- 过期；
- 无答案；
- 跨项目隔离。

指标：

- Recall@k；
- MRR；
- 无关注入率；
- 跨项目泄漏率；
- 注入 token；
- 延迟；
- Provider 调用次数。

## 6. P7-C：Durable Workflow 与 Provider 治理

### C1 统一内部 checkpoint

将以下阶段统一接入 `step_checkpoints`：

```text
plan
claim
verify
synthesize
write
```

每个阶段至少保存：

- `run_id`；
- `step_id`；
- `chain_phase`；
- `input_digest`；
- 输出 Artifact；
- attempt；
- 状态；
- 错误引用；
- 是否可恢复；
- 开始和结束时间。

### C2 统一恢复决策

将结果分为：

```text
request_not_sent
request_sent_no_response
response_received_not_persisted
response_persisted_delivery_failed
delivery_published
```

根据副作用类型决定：

- 自动重试；
- 复用 Artifact；
- 等待人工判断；
- 终止 Run。

### C3 动态工作流

在现有 DAG 和 Runtime 基础上补充：

- 条件分支；
- 动态追加步骤；
- 局部重规划；
- 人工审批节点；
- 子任务并行和汇聚；
- 任务暂停和继续。

不直接引入 Temporal。先验证现有 SQLite lease、checkpoint 和 outbox 是否能支撑目标场景。

### C4 Provider 可靠性

优先实现：

- 分层超时；
- 异步 HTTP/连接池；
- token 流式；
- 多 Provider failover；
- 熔断和半开恢复；
- Provider 级限流；
- 结构化 JSON Schema 解码；
- schema repair；
- 失败原因和 Provider 能力缓存。

所有路由决策写入 Run：

```text
provider
model
reason
fallback_chain
latency
usage
```

## 7. P7-D：工具生态与扩展能力

### D1 计算工具升级

当前 bootstrap 沙箱只适合单机研究工具。若要运行不可信代码，需要 OS 级隔离：

- 容器；
- Windows Job Object；
- 受限 Token；
- 文件系统隔离；
- 网络命名空间；
- CPU/内存/进程/文件数配额；
- 独立 Worker；
- 资源超限强制终止。

升级前必须明确威胁模型，不能把当前方案宣传为安全执行环境。

### D2 MCP 运行时治理

补充：

- 子进程健康检查；
- 崩溃重启；
- 调用超时；
- 工具 Schema 漂移检测；
- 工具版本和能力声明；
- 单工具限流；
- 失败熔断；
- 返回内容隔离；
- 外部写操作 HITL。

### D3 Skill 本地创建与版本化

第一批支持：

- Markdown/YAML 创建；
- 输入 Schema 编辑；
- 默认预算设置；
- 本地测试运行；
- 启用/停用；
- 版本号；
- 运行记录；
- 回滚。

暂不建设公开 Skill 市场。

### D4 统一 ToolResult

Skill、MCP、Compute 统一输出：

```text
ToolCall
ToolResult
PermissionDecision
Artifact
Evidence
Usage
```

Agent 只能引用状态明确、来源可追溯的工具结果。

## 8. P7-E：市场化部署能力

只有在确定要公网或多人部署时启动。

优先顺序：

```text
E1 鉴权与租户隔离
E2 Provider key 安全存储
E3 备份与恢复演练
E4 OTel trace、metrics、告警
E5 并发压测与 soak
E6 灰度、回滚和版本迁移
E7 ToS、频控和数据合规
```

### 上线阻塞标准

未完成以下项目，不应宣称可公网部署：

- API 鉴权；
- Artifact 访问控制；
- Provider key 不落日志；
- 备份可恢复；
- 队列积压可观测；
- Worker 崩溃可接管；
- 基础并发容量已知；
- 数据删除和保留策略明确。

## 9. 推荐 Gate 顺序

```text
Gate V1  A5/B1/C1/C2/W3 真实验证
Gate V2  状态文档和证据同步
Gate A1  全局搜索
Gate A2  PDF 研读联动
Gate A3  备份恢复迁移
Gate B1  记忆治理和反馈
Gate B2  记忆衰减与程序性记忆
Gate C1  内部阶段统一 checkpoint
Gate C2  Provider failover 与结构化解码
Gate D1  MCP/Skill 生命周期治理
Gate E1  公网部署安全和运维
```

每个 Gate 必须记录：

- 修改文件；
- 代码版本；
- 测试命令；
- 实际测试结果；
- 真实 Run 或浏览器证据；
- 失败案例；
- 未覆盖场景；
- 是否进入下一 Gate。

## 10. 优先级结论

### 近期优先

```text

→ 更新状态文档
→ 全局搜索
→ PDF/笔记联动
→ 备份恢复
```

### 中期优先

```text
记忆治理
→ 记忆衰减和反馈
→ Provider failover
→ 结构化输出解码

```

### 后期优先

```text
MCP 生命周期治理
→ Skill 本地创建和版本化
→ OS 级计算沙箱

```

### 单独市场化计划

```text
鉴权
→ 多租户
→ 备份演练
→ 可观测性
→ 压测
→ 灰度和回滚
```

## 11. 最终边界

当前系统已经适合继续作为个人研究型 Agent Workbench 使用和真实验证，但不应宣称已经具备：

- 完整七阶段 durable execution；
- 不可信代码安全执行；
- 多 Provider 生产级故障转移；
- 多用户 SaaS 能力；
- 公网部署级安全和运维成熟度。

后续路线的核心判断是：

```text
先完成已实现能力的真实验证，
再补研究者高频缺失功能，
随后统一执行、记忆和工具治理，
最后建设市场化基础设施。
```
