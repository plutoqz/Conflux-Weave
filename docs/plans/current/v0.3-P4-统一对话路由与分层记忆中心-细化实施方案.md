## 0. 这一份方案回答的核心问题

1. **为什么对话入口不能继续停留在一个被动的多选下拉框？**  
   目前用户在对话前必须手动在“直接提问(direct)”、“知识库问答(rag)”、“深度研究(deep)”之间做机械选择，且文档研读（DocumentAgent）、代码认知治理（ProjectAgent）分散在不同页面。研究者需要的是一个**全能统一入口（Omnibox）**：能够自动识别自然语言意图、解析 `@project` / `@paper` / `@note` 等实体上下文，并在“即时回答”与“长程研究 Run”之间自主分流。
2. **为什么智能路由必须坚持“快慢双通道解耦”？**  
   普通概念释义或知识点查询需要亚秒级首字吐出（快通道，Fast Path，零 Durable Run 开销）；而多源交叉研究、长篇学术论文精读、项目架构契约审计需要创建标准 Durable Run、统一 Harness 编排、保留完整的 Evidence/Claim 闭环与异步 SSE 状态可查性（慢通道，Slow Path）。两类任务在生命周期、计算开销和审计要求上完全异构，绝不能混为一谈。
3. **为什么长期记忆（Personal Memory）绝不能搞“全量原始对话暗中入库”？**  
   把多轮原始聊天记录无节制向量化或全量持久化，会导致：① 严重的上下文污染与幻觉放大；② 潜在的个人隐私泄露；③ 无法处理用户前后矛盾的需求演化。系统必须采用**原子化记忆候选机制（MemoryCandidate）**，仅提炼事实、偏好与约束，并经过系统去重与冲突检测。
4. **如何彻底杜绝“系统胡乱记忆”导致的使用体验崩塌？**  
   建立**人在回路（HITL - Human in the Loop）显式核准红线**。除当前会话内自动生效且会话结束即衰减的“会话临时记忆（Session Memory）”外，所有拟持久化的“用户偏好记忆（User Memory）”和“项目级约定记忆（Project Memory）”，必须以微卡片形式在界面向用户征询或在记忆中心显式核准，用户享有 100% 的审查、编辑与物理删除权。
5. **记忆上下文如何注入，才不至于挤占宝贵的上下文窗口并引发高昂成本？**  
   恪守紧凑预算控制原则（L0/L1 预算）：记忆注入块严格限制在 300~500 token 以内，按角色与任务动态提取最相关的条目，严禁无差别堆砌。

## 1. 核心设计原则与安全红线

1. **快慢通道分离与零摩擦降级 (Fast/Slow Decoupling & Graceful Degradation)**：
   - **快通道 (Fast Path)**：轻量直接问答与知识库片段问答，采用无重量级 Run 的流式直出，毫秒级响应；
   - **慢通道 (Slow Path)**：深度多源研究、长篇笔记连续修订、项目工程治理，创建标准 Durable Run，保留完整的 Evidence/Claim 闭环、取消、重试与可回放审计能力；
   - **手动覆写绝对优先**：模式选择器默认提供“✨ 智能路由 (Auto)”，但保留用户显式指定模式（Direct / RAG / Deep / Document / Project）的能力。用户显式指定时，路由器 100% 遵从，严禁强行拦截。
2. **三层记忆拓扑隔离与作用域封闭 (Strict Hierarchical Isolation)**：
   - **会话临时记忆 (Session)**：仅限单次会话或单个 Run 内有效，记录短程约束与指代信息，会话关闭或归档自动解除，不向全局扩散；
   - **项目级记忆 (Project)**：绑定特定 `project_id`，记录项目技术栈决策、特定论文结论、架构约定，跨项目严格隔离；
   - **用户全局记忆 (User)**：绑定全局用户身份，沉淀跨会话通用的学术研究领域、中文化输出文风、专业偏好。
3. **人在回路 (HITL) 与写入物理核准红线 (Explicit Human Approval)**：
   - Agent **只能提出记忆候选 (`MemoryCandidate`)**，无权直接将新长期记忆私自持久化生效；
   - 系统自动对候选条目进行精确去重与冲突判定；
   - 处于 `pending` 状态的长期记忆候选必须经由用户显式核准（Approve）后方可转化为生效记忆（`active`）。
4. **纯本地离线与零外部 CDN 保证 (100% Offline Native)**：
   - 全面沿用原生 Vanilla ESM 规范与 CSS 变量体系，零外部 CDN，保持 100% 本地离线运行；
   - 保证既有 16 条运行端点、SSE 协议和 555 个测试用例向前兼容。

### 支柱 1：分层记忆拓扑架构与生命周期 (Hierarchical Memory Topology)

记忆分为三层，层级越低作用范围越广、持久性越强，审查门槛越高：

```text
+-----------------------------------------------------------------------+
| 用户全局记忆 (User Memory) · 长期持久化                                |
| • 学术领域 ("研究方向聚焦大模型幻觉治理与长上下文检索")               |
| • 文风偏好 ("回答保持严谨客观，关键论点给出文献引用与代码行号")       |
| • 语言习惯 ("优先中文学术术语表达，核心专业词汇保留英文对照")         |
+-----------------------------------▲-----------------------------------+
                                    │ (显式用户核准)
+-----------------------------------┴-----------------------------------+
| 项目级记忆 (Project Memory) · 绑定 project_id                          |
| • 技术约定 ("检索模块统一采用 RRF 倒数排序融合")                      |
| • 架构决策 ("对外服务只暴露 16 条 REST 端点，不引入 Web IDE")         |
| • 核心结论 ("已证明 PyMuPDF 抽图性能显著优于 pypdf")                  |
+-----------------------------------▲-----------------------------------+
                                    │ (显式用户核准)
+-----------------------------------┴-----------------------------------+
| 会话临时记忆 (Session Memory) · 单次会话生命周期                       |
| • 短程上下文约束 ("本次讨论限定在 Section 3 的公式推导")              |
| • 代词指代消除 ("这里的'它'指的是 DocumentNote 乐观锁机制")            |
| • 随 Conversation 归档或关闭自动注销，零跨会话泄漏                     |
+-----------------------------------------------------------------------+
```

1. **记忆候选提炼 (`MemoryCandidate`)**：
   - 交互过程中，`MemoryAgent` 异步分析用户输入与交付交互；
   - 仅当识别出明确的陈述句（“以后回答都用中文”、“本项目核心算法是 RRF”）时才提炼为候选；
   - 提取属性：`scope` (user / project), `category` (preference / constraint / fact / decision), `statement`, `confidence` (0.0~1.0), `source_context`。
2. **冲突检测与去重更新 (Deduplication & Conflict Detection)**：
   - **完全重复**：若新陈述与已有记忆哈希一致，仅刷新 `updated_at` 与更新频次计数；
   - **语义冲突**：若检测到相反语义（例如用户之前设定“默认输出代码段”，当前表达“不要贴任何代码”），系统将已有记忆标记为 `conflict_with_memory_id`，在前端提示“发现与历史偏好存在冲突，是否覆盖更新？”。
3. **人在回路核准与维护操作**：
   - 记忆候选在前端以微卡片显示，支持：【保存为偏好】、【本次忽略】、【不再提示】；
   - 用户可在“设置 -> 记忆中心”中进行全量查看、就地编辑陈述文本、修改作用域或物理删除。

### 支柱 2：统一对话路由器与快慢通道解耦 (ConversationRouter)

将零散的提交逻辑聚拢于统一的意图路由引擎：

1. **统一输入规约 (Omnibox Input Protocol)**：
   - 接受用户自然语言输入，支持内联实体标记（如 `@project:Conflux-Weave`、`@paper:2606.08702`、`@note:note-1`）；
   - 支持显式命令前缀快捷覆写（如 `/deep 量子退火在排产中的应用`、`/audit 契约审计`、`/rag 本地知识库`）。
2. **两阶段意图分类体系 (Two-Stage Intent Classification)**：
   - **第一阶段（确定性规则匹配，零开销）**：
     - 用户下拉框若手动指定了模式（`direct` / `rag` / `deep` / `document` / `project`），直接 100% 采纳；
     - 检测到以 `/` 开头的指令，直接映射为对应模式；
     - 检测到 `@project` 实体，默认进入 `project` 意图；检测到 `@paper`，默认进入 `document` 意图。
   - **第二阶段（轻量模型意图分类，仅当处于 Auto 模式）**：
     - 调用低温度轻量 Prompt，分类输出：
       - `direct`（普通问候、常识、概念解释、语法检查）；
       - `rag`（针对本地论文库、特定文献细节的提问）；
       - `deep`（长程多源调研、行业现状综述、对比分析报告）；
       - `document`（针对单篇论文的深度笔记、结构化拆解）；
       - `project`（针对代码库结构、Git 差异、实现审计）；
       - `memory`（用户主动询问“你记住了我什么偏好”或“修改我的输出语言”）。
3. **快慢通道分流执行策略**：
   - **快通道 (`direct` / `rag` / `memory`)**：
     - 服务端直接执行流式返回或轻量应答，不向 SQLite 写入重量级 `tasks` 与 `runs` 表，仅写入 `chat_messages`；
     - 前端立即渲染气泡，亚秒级首字呈现。
   - **慢通道 (`deep` / `document` / `project`)**：
     - 服务端创建标准的持久化 `Task` 与 `Run`，分配 Run ID 与任务凭据；
     - 前端对话窗口立即渲染可交互的“运行中 Run 演播卡片”，无缝对接 SSE 事件流广播，实时展示思考轨迹、工具调用与证据生成；
     - 运行完成后，产出完整的交付 Artifact（报告、笔记或审计单），用户可一键在对话中展开或跳转至对应专业工作台。

### 支柱 3：动态上下文注入与紧凑预算控制 (Dynamic Context Injection)

严防记忆堆积导致上下文膨胀：

1. **分层过滤与角色感知挂载**：
   - **通用规则**：所有 Agent 在初始化 System Prompt 时，先注入已核准的 `user_memory`（偏好与文风）；
   - **项目上下文**：当任务关联特定 `project_id` 时，自动追加挂载 `project_memory`（技术约定与架构边界）；
   - **会话上下文**：当前 Conversation 的 `session_memory` 紧跟用户 Query 前挂载。
2. **L0/L1 紧凑预算硬上限 (Hard Token Budget)**：
   - 记忆注入块在提示词中拥有严格的 token 配额：**总长度严控在 300 ~ 500 token 以内**；
   - 当记忆条目过多时，按 `confidence`（置信度）降序与 `updated_at`（最近使用）排序截断，保留核心要点，拒绝全量灌入；
   - 格式化规约：
     ```text
     【经用户核准的个性化与项目约定】
     - [偏好] 回答严谨客观，避免夸大词汇，尽量使用中文学术术语。
     - [约定] 本项目检索采用 RRF 倒数排序融合机制。
     ```

### 支柱 4：全能工作台演播室与记忆管理交互 (Workbench Omnibox & Memory Studio)

1. **全能对话输入框 (The Omnibox)**：
   - 居中自适应高度输入框，支持 `@` 自动补全浮窗（选择当前已收录的论文、项目、笔记）；
   - 模式选择器首位呈现：“✨ 智能路由 (Auto)”；
   - 发送后，若处于 Auto 模式，输入框下方即时呈现路由决策徽标（如：`⚡ 已分流至直接问答`、` 本地资料库问答`、` 正在创建深度研究 Run...`），给用户清晰的确定性感。
2. **记忆候选通知气泡 (Memory Notification Bubble)**：
   - 当回复生成后，若探测到高置信度的偏好陈述，在对应 Assistant 消息下方轻量悬浮提示：
     ```text
     💡 记住了你的偏好：“回答保持严谨，使用中文学术术语”
     [ 核准记住 ]  [ 忽略 ]
     ```
3. **设置中心 · 分层记忆管理中心 (Memory Center)**：
   - 在设置视图（`#/settings`）中新增专属管理面板：
     - **用户偏好记忆区**：卡片式罗列全局偏好，支持添加、修改内容、一键注销；
     - **项目约定记忆区**：下拉选择项目，查看该项目的架构约定与决策记忆；
     - **待核准候选列表**：集中展示近期对话中发现的候选，支持批量批准或一键清空；
   - 遵循 Moss 设计系统风格，支持暗黑/明亮主题自适应与移动端友好交互。

## 3. 数据合同与架构落点

### 3.1 核心数据结构

```python
# 1. 记忆作用域与类别枚举
class MemoryScope(str, Enum):
    SESSION = "session"      # 会话临时
    PROJECT = "project"      # 项目约定
    USER = "user"            # 用户全局

class MemoryCategory(str, Enum):
    PREFERENCE = "preference"  # 用户偏好/文风
    FACT = "fact"              # 经确认的客观事实
    CONSTRAINT = "constraint"  # 规约与限制
    DECISION = "decision"      # 架构/技术决策

class MemoryStatus(str, Enum):
    ACTIVE = "active"          # 已生效
    ARCHIVED = "archived"      # 已废弃/归档

class CandidateStatus(str, Enum):
    PENDING = "pending"        # 待核准
    APPROVED = "approved"      # 已核准入库
    REJECTED = "rejected"      # 已拒绝

# 2. 长期记忆持久化条目
@dataclass(frozen=True, slots=True)
class MemoryItem:
    memory_id: str
    scope: MemoryScope
    target_id: str             # user_id 或 project_id
    category: MemoryCategory
    statement: str
    confidence: float          # 0.0 - 1.0
    status: MemoryStatus
    source_type: str           # "conversation" | "manual" | "run"
    source_id: str             # conversation_id | run_id
    created_at: str
    updated_at: str

# 3. 记忆候选条目
@dataclass(frozen=True, slots=True)
class MemoryCandidate:
    candidate_id: str
    scope: MemoryScope
    target_id: str
    category: MemoryCategory
    statement: str
    confidence: float
    conflict_with_memory_id: str | None
    status: CandidateStatus
    source_type: str
    source_id: str
    created_at: str

# 4. 统一对话路由结果
@dataclass(frozen=True, slots=True)
class RouterResult:
    target_mode: str           # "direct" | "rag" | "deep" | "document" | "project" | "memory"
    is_fast_path: bool         # True: 快通道免 Run; False: 慢通道持久化 Run
    confidence: float          # 0.0 - 1.0
    intent_summary: str        # 人话路由决策理由
    extracted_entities: dict[str, str]  # 如 {"project_id": "...", "paper_id": "..."}
    suggested_run_kind: str | None      # 如 "managed_verified_research"
```

### 3.2 数据库迁移规约 (SQLite Migration v7)

在 `src/conflux_weave/runtime/sqlite_migrations.py` 中追加 `version=7`：

```sql
-- Migration 7: v03_hierarchical_memories
CREATE TABLE memories (
    memory_id TEXT PRIMARY KEY,
    scope TEXT NOT NULL CHECK (scope IN ('session', 'project', 'user')),
    target_id TEXT NOT NULL,
    category TEXT NOT NULL CHECK (category IN ('preference', 'fact', 'constraint', 'decision')),
    statement TEXT NOT NULL,
    confidence REAL NOT NULL DEFAULT 1.0,
    status TEXT NOT NULL DEFAULT 'active' CHECK (status IN ('active', 'archived')),
    source_type TEXT NOT NULL,
    source_id TEXT NOT NULL,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL
);

CREATE INDEX idx_memories_lookup
ON memories(scope, target_id, status, category);

CREATE TABLE memory_candidates (
    candidate_id TEXT PRIMARY KEY,
    scope TEXT NOT NULL CHECK (scope IN ('session', 'project', 'user')),
    target_id TEXT NOT NULL,
    category TEXT NOT NULL CHECK (category IN ('preference', 'fact', 'constraint', 'decision')),
    statement TEXT NOT NULL,
    confidence REAL NOT NULL DEFAULT 0.8,
    conflict_with_memory_id TEXT REFERENCES memories(memory_id) ON DELETE SET NULL,
    status TEXT NOT NULL DEFAULT 'pending' CHECK (status IN ('pending', 'approved', 'rejected')),
    source_type TEXT NOT NULL,
    source_id TEXT NOT NULL,
    created_at TEXT NOT NULL
);

CREATE INDEX idx_memory_candidates_status
ON memory_candidates(status, scope, target_id);
```

## 6. 分阶段实施路线图与验收评测矩阵

整个 P4 实施分为 5 个严密演进的里程碑切片，每个切片严格遵守先自动化单测、后浏览器无头走查、全量回归不降级的交付标准：

### 阶段 P4.0：细化方案与架构契约冻结（本方案）
- **目标**：冻结三层记忆拓扑模型、统一路由分流机制、API 契约及 SQLite Migration v7 规范；
- **验收标准**：文档经评审确认，纳入 `docs/plans/current/` 权威受控目录。

### 阶段 P4.1：分层记忆中心核心引擎与存储落地（记忆基石）
- **目标**：
  - 实现 SQLite Migration v7（`memories`, `memory_candidates`）；
  - 实现 `HierarchicalMemoryStore`，支持 CRUD、去重哈希、冲突检测；
  - 实现 `MemoryAgent`：提示词候选提取器、冲突分类器、L0/L1 紧凑上下文格式化器；
  - 挂载 `/api/v1/memories` 与 `/candidates` REST API；
- **验收标准**：
  - 单元测试覆盖三层隔离、冲突判定、HITL 核准流程；
  - 迁移测试验证 v6 -> v7 平滑升级与回滚安全。

### 阶段 P4.2：统一对话路由引擎 (ConversationRouter)
- **目标**：
  - 实现 `ConversationRouter`：规则快速匹配器（前缀、`@` 实体）、轻量 LLM 意图分类器、快慢通道分流器；
  - 升级 `server.py` 与 `chat.py`：`/api/v1/chat` 支持 `mode="auto"`，完成与既有 direct/rag/deep 以及项目工作台的平滑路由适配；
- **验收标准**：
  - 构造离线意图评测基准集合（覆盖常见 30 条自然语言典型输入），路由准确率 ≥ 95%；
  - 异常/无网络场景下 100% 确定性安全降级为 `direct`。

### 阶段 P4.3：端到端 Agent 记忆感知与上下文注入
- **目标**：
  - `ResearchAgent`、`DocumentAgent`、`ProjectAgent` 在初始化运行时，通过 `MemoryAgent` 自动挂载上下文；
  - 严格限制记忆注入 token 消耗（≤ 400 token）；
  - 实现跨 Run 偏好延续与会话临时事实隔离；
- **验收标准**：
  - 回归测试验证：在设定“文风偏好”后，生成的回答或报告严格遵守该偏好约束。

### 阶段 P4.4：全能工作台前端交互重塑 (Omnibox & Memory Studio)
- **目标**：
  - 重塑 `modules/chat.js`：Omnibox 输入框、`@` 实体联想浮层、路由意图状态徽标；
  - 增加消息气泡下方的“记忆候选通知”交互组件（支持一键核准/忽略）；
  - 升级 `modules/settings.js`：落地分层记忆管理面板（用户偏好、项目约定、候选抽屉）；
- **验收标准**：
  - 桌面端（1440x900）与移动端（390x844）走查零水平溢出、零控制台错误；
  - 满足 100% 纯本地无外部 CDN 契约。

### 阶段 P4.5：全链路冻结评测与验收交付
- **目标**：
  - 执行包含快速问答、知识检索、深度研究、代码治理的端到端混合测试；
  - 运行全量自动化测试，确保原有 555 个测试全部绿灯；
  - 更新项目状态矩阵（`docs/status/project-status.md`）。
- **验收标准**：
  - 全套回归测试全部通过，产出正式的 P4 验收报告。
