> 状态：`validated_live`
>
> 日期：2026-08-24

> 设计依据：`docs/design/current/Conflux-Weave设计文档v0.2.md`

>
> 最终边界：W2.0-W2.4 已完成 `validated_offline`，W2.5 已完成受限
> `validated_live`。不声明跨数据库综述、全文核验、通用多源 RAG、embedding
> 或生产能力。

## 1. 目标、主张与原则

W2 不是增加产品页面或 Agent 角色，而是把 W1 的最小查询链路提升为更有用的
检索和交付：

```text
研究问题 -> 检索/抓取 -> Evidence -> 任务级回答 -> 可信度和限制标记
```

阶段主张是：系统能够在冻结来源和预算范围内尽可能搜集足够信息、解答用户问题，
并分别标注回答内容的证据支持状态与来源可信度。证据优先意味着不伪装确定性，
不意味着没有声明级 Citation 就拒绝回答。

W2 的验收优先级固定为：

1. 用户任务是否得到可用交付；
2. 关键事实是否有足够 Evidence 和可打开定位；
3. 证据不足、冲突和来源质量是否可理解；
4. 正文是否保持连续可读；
5. 检索指标和内部诊断是否支持具体实现决策。

## 2. 结果语义冻结

### 2.1 任务结果与证据状态分离

任务结果、证据支持状态和来源可信度是三个独立维度：

| 层次 | 允许值 | 含义 |
|---|---|---|
| 任务结果 | `complete` | 主要任务完成，关键事实获得充分支持 |
| 任务结果 | `partial` | 有可交付回答或证据片段，但存在明确未满足条件 |
| 任务结果 | `no_answer` | 当前合同和硬约束下无法负责任地回答任务核心问题 |
| 证据支持 | `cited` | 关键事实 Claim 可定位到 Evidence 和 SourceSnapshot |
| 证据支持 | `partial_support` | 有相关 Evidence，但覆盖、范围或强度不足 |
| 证据支持 | `uncited_context` | 背景、方法建议或一般性解释，不作为当前来源事实交付 |
| 证据支持 | `conflicting` | Evidence 之间冲突，必须暴露冲突或降低结论强度 |
| 证据支持 | `unsupported_claim` | 当前来源不能支持该事实 Claim，不得用确定语气交付 |
| 来源可信度 | `authoritative` | 官方、一手资料或明确责任主体发布 |
| 来源可信度 | `credible_secondary` | 可核验的同行评审、机构或专业二手来源 |
| 来源可信度 | `general_source` | 可定位但权威性有限的一般来源 |
| 来源可信度 | `unverified_source` | 来源身份、维护关系或质量尚未独立核验 |

必须遵守：

- 没有声明级 Citation 不自动等于 `no_answer`。
- 有部分 Evidence 时优先形成 `partial`，同时列出未满足条件。
- `uncited_context` 可以进入回答，但必须与来源事实在语义和展示上分开。
- 有 Citation 只说明可以定位，不等于来源可信。
- 已作为事实 Claim 交付的内容必须通过内部闭合校验；这不要求每句话或每个段落
  后附 Citation。
- 只有无法对任务核心问题作出负责任回答时才使用 `no_answer`。

### 2.2 典型组合

| 情况 | 任务结果 | 处理 |
|---|---|---|
| 关键事实有定位，来源为官方或一手 | `complete` | 正文自然呈现，回答块标记支持和来源等级 |
| 有相关材料但缺少一部分关键来源 | `partial` | 交付已支持部分，列出未满足条件 |
| 证据不足，但可以提供一般背景解释 | `partial` 或受限 `complete` | 背景标为 `uncited_context`，降低措辞，不伪装成来源结论 |
| 来源可定位但身份未核验 | `partial` | Citation 与 `unverified_source` 分开显示 |
| 来源互相冲突 | `partial` | 显示冲突，给出各方定位和待核验动作 |
| 当前约束下没有任何负责任的任务级答案 | `no_answer` | 说明硬约束、证据边界和恢复选项 |

## 3. 交付展示合同

### 3.1 低干扰标记

引用不附在每句话或每个段落后面。正文以回答块、主要结论或小节为单位显示紧凑
标记，并在报告开头提供一次图例；完整定位放入 Evidence 汇总。

默认标记如下，实施时只允许做不改变语义的视觉调整：

| 维度 | 标记 | 含义 |
|---|---|---|
| 证据支持 | `●` | 有声明级 Evidence/Citation |
| 证据支持 | `◐` | 部分支持或范围受限 |
| 证据支持 | `○` | `uncited_context`，不是当前来源事实 |
| 证据支持 | `!` | 存在冲突或重要限制 |
| 证据支持 | `?` | 当前来源不支持，待核验 |
| 来源可信度 | `A` | authoritative |
| 来源可信度 | `C` | credible_secondary |
| 来源可信度 | `G` | general_source |
| 来源可信度 | `?` | unverified_source |

例如一个回答块可以只显示一次 `● A` 或 `◐ C`；用户需要核查时，再从标记或
汇总表打开 Claim、Evidence、SourceSnapshot 和精确 locator。不得在正文中重复打印
相同来源的长 URL、页码或 Citation 编号，以免破坏阅读节奏。

### 3.2 内容分层

生成器或渲染器必须能区分：

1. 关键事实 Claim：进入 Evidence/Citation 闭合校验；
2. 受限事实：进入 `partial_support`、`conflicting` 或 `unsupported_claim`；
3. `uncited_context`：允许帮助用户理解，但不得被表述为当前来源已证实；
4. 限制、冲突和恢复建议：作为结果元信息展示，不冒充 Evidence。

## 4. 检索和数据范围

### 4.1 检索策略

先用 W1 固定工作流建立可复现基线，再只选择一个实际需要的策略：

- BM25：词项和实体边界明确时的确定性基线；
- Dense：同义表达和语义改写是主要失败原因时使用；
- RRF：只有 BM25 与 Dense 的案例级互补已被证明，且融合结果能改变产品决策时使用。

不在 W2 同时建设三套可配置检索平台，不以 Hit@K 的单独提高作为成功标准。

### 4.2 来源入口

- 保留 W1 的本地文档和 GitHub 入口；
- 增加一个最小 Web Search + Fetch 链路；
- 保存搜索查询、候选排序、选中来源、原始响应、来源身份、抓取时间和内容 hash；
- 搜索候选是发现 Artifact，只有被选中且登记的来源进入 Evidence；
- 来源可信度只来自可记录的身份或出版/维护信息，不由模型自报置信度替代。

### 4.3 案例集

W2 迁移 W1 相关案例并新增两类任务的 held-out 案例，至少覆盖：

- 论文发现与相关性边界；
- 论文或项目证据问答；
- 无答案；
- 部分证据；
- 来源身份未核验；
- 证据冲突；
- 具有可用 `uncited_context` 的回答。

案例必须保存输入 hash、来源边界、预期任务结果、可接受的证据状态和完成边界。

### 4.4 混合检索与 Agent RAG 准入门

以下能力有决策门，但不是按时间自动建设的必做路线：

| 候选能力 | 最早复核点 | 准入证据 | 当前决定 |
|---|---|---|---|
| Dense 检索 | W2.4 | 冻结 held-out 出现可复现的词法召回失败，且真实 embedding 配置已授权 | 暂缓 |
| BM25 + Dense + RRF | W2.4 或 W6 | 两个独立排序器各有互补收益，融合能改善真实任务且成本可接受 | 暂缓 |
| Reranker | W2.4 或 W6 | 候选召回充分但前列排序持续错误，Reranker 能改变交付质量决策 | 暂缓 |
| 多向量库 | W6 | 出现第二个真实垂直切片，且单一向量库不能满足数据隔离、索引或部署约束 | 非首版目标 |
| Agent RAG | W4 后 | bounded Agent 在冻结任务上优于 Fixed Workflow，且成本、延迟和失败率无不可接受回归 | 非默认路线 |
| 通用多源 RAG 平台 | W6 | 至少两个真实垂直切片共享稳定合同，抽象能消除已发生的重复 | 非首版目标 |

受限路径效果不佳只是调查触发条件，不自动授权上述能力。必须先定位失败属于数据、
分段、query 理解、召回、排序、上下文构造还是生成；只有根因与候选能力匹配，并有
案例级前后证据时才准入。Prompt、重试、额外向量库或 Agent 编排不能用来掩盖未定位
的结构问题。

## 6. 验证与证据要求

离线验证至少覆盖：

- 关键事实 Claim 的 Citation 闭合、唯一性和 locator 可解析；
- `uncited_context` 不被编译为已支持 Claim；
- `partial`、`no_answer`、冲突和来源失败的结果语义；
- Citation 存在与 source_trust 分离；
- 低可信来源不会因有 Citation 被提升为可信；
- 符号图例、回答块级标记和汇总表能共同表达状态；
- 正文不逐句或逐段附 Citation，且主要结论仍可扫描；
- 检索策略变更保留前后输入、配置、结果、指标和决定。

真实验证必须保留：Provider、模型、Prompt、参数、预算、查询、来源、原始响应、
失败、Evidence、Citation、标注产物和 hash。测试、HTTP 成功或回放不能替代真实用户
任务验收。

Ragas 只有在确定性结果无法回答一个已经出现的 Retrieval/Evidence 产品风险时才可
接入；接入申请必须说明 `Feature`、`Risk`、`Question`、`Metric`、`Decision`、
`ActionOnFail` 和 `StopCondition`。

## 7. 实施顺序、回滚与停止条件

实施顺序固定为：

1. 冻结并校验结果语义、案例 schema 和展示合同；
2. 建立 W1 检索基线，选择一个实际需要的策略；
3. 增加单一 Web Search + Fetch 和 Evidence Locator v1；
4. 实现 Claim 支持、来源可信度和回答块级标记；
5. 运行确定性案例、held-out 对比和必要的 Ragas admission；
6. 在授权、Provider、预算和网络条件齐备后完成三次真实任务验收。

每个步骤保留旧 Artifact 和 manifest。检索或展示变更导致关键任务回归时，恢复到
上一个 manifest 和策略版本，不覆盖历史运行；无证据的修复不能通过增加重试、放宽
硬约束或单案例特判来伪造成功。

立即停止并报告：

- 为增加来源、格式或 Agent 角色而延迟两个真实任务类型的可用交付；
- 逐句 Citation、Ragas、Phoenix 或评测看板成为黄金路径前置；
- Evidence 定位、来源身份或结果语义未解决，却连续只调整 Prompt、重试或案例特判；
- 指标不能改变具体检索、证据或展示决策仍继续扩充评测；
- live 验证缺少用户授权、Provider/模型/预算或网络授权。

## 8. W2.1 实际结果

W2.1 使用 `src/conflux_weave/retrieval.py` 建立了一个窄的、无外部依赖的 BM25
Retriever。它保留 `document_id`、`source_snapshot_id` 和 `locator`，排序分数和同分
时的文档 ID 都是确定的；检索模块只负责排名，不复制 Evidence 或回答语义。

冻结的两个确定性案例覆盖上下文管理和消息工作流检索。结果为：

| 策略 | Recall@2 | MRR | 状态 |
|---|---:|---:|---|
| BM25 | 1.0 | 1.0 | 已实现并评估 |
| Dense | - | - | 未评估：没有 embedding 模型、语义 held-out 语料或 Provider 授权 |
| RRF | - | - | 未评估：没有第二个独立排序列表，融合会凭空增加复杂度 |

这两个案例只证明离线排序机制和当前 fixture 的基线结果，不证明真实来源检索、
语义召回或在线能力。完整记录见 `docs/plans/archive/W2.1-检索基线评估.json`。

选择 BM25 的原因是当前冻结切片包含明确实体和术语，BM25 已足以提供可复现基线，
且能把来源定位元数据无损传递给下一阶段 Evidence Locator。只有出现已冻结的词法
失败案例、真实 embedding 配置和具体产品决策时，才重新评估 Dense；只有存在两个
独立排序列表且融合能改变决策时，才评估 RRF。

## 9. W2.2 实际结果

W2.2 保留现有 GitHub 搜索适配器作为发现入口，新增
`src/conflux_weave/web.py::WebFetchAdapter` 作为受限 Fetch 入口。Fetch 过程：

```text
URL -> raw response Artifact -> UTF-8 normalized text Artifact
    -> SourceSnapshot -> paragraph segments -> text_range locator
```

每个段落 locator 包含 `start_char`、`end_char` 和 `text_sha256`，可以在不可变的
规范化文本 Artifact 中复核；HTML 会排除 script/style 等非正文内容，纯文本保留
段落边界。HTTP 错误、网络错误、编码错误、空正文和超大响应都 fail closed，并保留
已有诊断或原始响应引用；不自动 retry 或 fallback。

5 个确定性 Fetch 测试和 W1 GitHub 搜索测试均通过。完整记录见
`docs/plans/archive/W2.2-Web-Fetch验收.json`。本验收只证明 fixture transport 下的
离线合同和定位机制，不证明公共网络可访问性、网页 JavaScript 渲染或 Provider 能力。

## 10. W2.3 实际结果

W2.3 新增 `src/conflux_weave/evidence/delivery.py`，将回答块的证据支持状态和来源
可信度分开建模。内部事实 Claim 仍经过 `require_closed_citations`；`uncited_context`
和 `unsupported_claim` 不允许注册为有来源事实 Claim。

仓库身份报告和 PDF 阅读笔记报告已迁移到统一渲染器。正文以回答块显示一次
`●/◐/○/!/?` 和 `A/C/G/?`，不再在每条声明后追加 `[n]`；完整 Claim、Evidence、
SourceSnapshot 和 locator 只在末尾 Evidence 汇总中出现。该改变不删除 Citation，
只改变用户可见编排。

16 个聚焦测试通过，覆盖 `uncited_context`、低可信但有 Citation、Claim 闭合和两条
报告入口。完整记录见 `docs/plans/archive/W2.3-可信交付验收.json`。当前是离线 fixture
证据，尚未经过新的真实任务阅读体验验收。

## 11. W2.4 实际结果

W2.4 完整迁移了 legacy multilingual RAG 的 30 条输入，并增加 5 条 W2 结果边界
案例。新数据集位于 `datasets/regression/w2-retrieval-evidence-v1.0.0/`。其中 27 条
来源存在，可进入离线检索对比；3 条引用缺失的 legacy 来源被原样保留并标为
`missing/partial`。每种语言的 009/010 共 6 条作为 held-out，不参与修复方向选择。

数据集仍为 `provisional`：迁移已复核 schema、来源存在性和 hash，但 legacy 语义标签
与由 source id、`must_contain` 构造的 corpus 尚未经过独立人工复核。因此结果只证明
排序和合同机制，不是答案质量 gold。

首轮 CJK unigram/bigram 结果因混合语言噪声下降，且发现 Retriever 将零分文档放入
top-k 的评估缺陷；该轮被拒绝并保留。修复零分候选、中文 unigram/bigram 和混合查询
Latin 实体优先后，接受结果为：

| Slice | Before Recall@3 | After Recall@3 | Before MRR | After MRR |
|---|---:|---:|---:|---:|
| Overall 27 | 0.704 | 0.778 | 0.599 | 0.685 |
| Held-out 6 | 0.833 | 0.833 | 0.556 | 0.639 |
| zh-zh 10 | 0.600 | 0.800 | 0.550 | 0.733 |

仍有 6 条未召回：4 条 `zh-en`、1 条中文 GIS 和 1 条 held-out 中文量子密码案例。
这些是 Dense 的候选消费者，但 provisional constructed corpus 不足以授权 embedding
实现。W2.5 若在真实任务中复现跨语言或语义召回失败，再冻结 embedding、预算和
前后对比。

Ragas 本阶段不准入：确定性 Recall/MRR 和逐案例 rank 已经回答当前检索决策，Ragas
不能定位 missing retrieval hit。RRF 因没有第二个独立排序列表不准入；Reranker 因
当前问题属于召回缺失而非已证明的头部排序错误不准入。

完整记录见 `docs/plans/archive/W2.4-离线评估验收.json`；原始结果保存在 Git 忽略的
`var/evaluations/w2.4/offline-comparison.json`。

## 13. W2.5 Live 冻结与执行入口

W2.5 已由用户明确授权，精确任务、Provider、预算、来源边界、失败语义和代码文件
hash 冻结在 `docs/plans/archive/W2.5-live-freeze.json`。三次 Run 按顺序覆盖：

1. Agent/LLM 上下文管理论文发现；
2. `pi coding agent` 项目身份与证据问答；
3. GIS/地理空间分析 Agent 论文发现及相关性边界。

论文发现使用新的 bounded arXiv Atom 入口，流程固定为：

```text
arXiv query -> raw Atom Artifact -> SourceSnapshot -> BM25 selection
    -> item Evidence -> one Provider call -> closed Citation -> readable report
```

每个 Run 最多一次 Provider 调用、最多 2,048 output tokens，禁用 thinking，不自动
retry、不 fallback。arXiv 结果只支持预印本身份、元数据、摘要内容和摘要级相关性判断；
GitHub 结果只支持候选仓库元数据和 README 自述，不能把搜索排名提升为官方关系证明。

任一 Run 失败时保留错误和已写入的原始 Artifact，该 Run 与 W2.5 均不通过；不得在
同一 Run 内改检索式、换来源或增加调用来补救。三次结果只有同时满足可用交付、
Evidence/Citation 闭合、可信度区分、低干扰正文、原始响应与 hash 保留、秘密扫描通过，
才能把 W2.5 更新为 `validated_live`。

### 13.1 实际运行结果

三次 Run 均按冻结配置执行，每次一次 Provider 调用，总 output tokens 为 1,882；所有
来源响应、Provider 请求/响应、报告和 manifest 均保存为 SHA-256 Artifact，API key
扫描结果为 0。前两次内容审计通过：上下文管理论文任务交付 3 条直接相关结果，项目
证据问答定位到 `earendil-works/pi` 并保留官方关系未核验边界。

第三次 GIS/地理空间论文任务形成了结构完整的 `partial` 报告，但模型在限制中声称
所有 arXiv 记录“尚未经历正式同行评审或期刊出版流程”。Atom 元数据不能证明这一
状态，且该表述违反冻结 Prompt，因此本 Run 内容验收被拒绝，W2.5 保持
`executed_live_not_accepted`。失败报告和原始响应没有删除，也没有重试。

根因定位为生成后合同校验缺口：原实现校验 JSON、Evidence ID 和 Citation 闭合，
但未确定性拒绝发表/同行评审状态声明。现已增加
`paper_publication_status_unsupported` 校验及回归测试；该修复只有离线证据，尚未进行
新的 live 复验。完整记录见 `docs/plans/archive/W2.5-live验收.json`。

### 13.2 第一次修复后复验

`W2.5-LIVE-03-R1` 使用修复后的确定性校验执行了一次新 Run。Provider 再次输出
“尚未经历正式同行评审或期刊/会议出版流程”，工作流以
`paper_publication_status_unsupported` 拒绝交付，并保留请求与原始响应；没有 retry
或 fallback。由此证明错误状态声明不会继续进入用户报告，但 GIS 用户任务仍未形成
可用交付，因此 W2.5 继续保持 `executed_live_not_accepted`。

R1 进一步定位出旧 user prompt 的“保留预印本边界”与 system prompt 的禁止发表状态
推断存在语义张力，同时发现失败路径未提交统一 failure manifest。现已将 Prompt 升级
为 `arxiv-relevance-claims-zh-v2`，明确只说明 arXiv 元数据/摘要证据边界，并在结构
校验失败时提交包含 Run、来源、Provider 和 usage 的失败 manifest。聚焦测试 5 条通过，
但这些仍是离线修复证据。下一验收点为另行冻结 `W2.5-LIVE-03-R2` 并执行一次 live
复验。完整记录见 `docs/plans/archive/W2.5-R1-live验收.json`。

### 13.3 第二次修复后复验

`W2.5-LIVE-03-R2` 使用 Prompt v2 执行后，Provider 仍在 limitations 中输出了
“未包含……同行评审状态”。工作流按冻结合同拒绝交付，并成功提交 failure manifest；
该 manifest 完整关联 `run_id`、配置、arXiv SourceSnapshot、Provider 请求/响应和 usage，
证明 R1 后补充的失败追溯合同在 live 环境有效。没有 retry 或 fallback。

R2 的 8 条论文相关性 Claim 本身未触发边界校验，失败只来自模型生成的 limitations。
因此不再继续微调否定措辞，而是移除这一不必要的模型职责：Prompt v3 只允许输出
`claims`，来源覆盖、摘要级证据、全文和跨数据库限制由工作流确定性生成；发表状态
拒绝校验仍保留为 Claim 越界的最后防线。聚焦测试 6 条通过，尚未 live 复验。

W2.5 继续保持 `executed_live_not_accepted`。下一验收点为另行冻结
`W2.5-LIVE-03-R3`，验证 claims-only Prompt v3 能否形成 GIS 用户任务的可用交付。
完整记录见 `docs/plans/archive/W2.5-R2-live验收.json`。

### 13.4 第三次修复后复验与 W2.5 关闭

`W2.5-LIVE-03-R3` 使用 claims-only Prompt v3 执行成功，形成 `partial` 交付。Provider
原始 JSON 只包含 `claims`；8 条 Claim、8 条 Evidence 和 8 条 Citation 完整闭合。
报告明确区分直接 GIS/空间分析、基准、地理空间约束集成、数据管理和遥感/多模态
工作，正文仅显示一次 `◐ G`，完整定位集中在 Evidence 汇总。

来源限制由工作流确定性生成，没有发表或同行评审状态推断。一次 Provider 调用使用
3,888 input tokens 和 724 output tokens；7 个 manifest 引用和报告 Artifact 均存在，
API key 扫描为 0，无 retry 或 fallback。

W2.5 最终接受的三次任务为 `LIVE-01`、`LIVE-02` 和 `LIVE-03-R3`，覆盖论文发现与
项目证据问答两类任务。原始 `LIVE-03`、R1 和 R2 继续作为失败、拒绝和恢复证据保存。
因此 W2.5 与 W2 更新为 bounded `validated_live`。完整记录见
`docs/plans/archive/W2.5-R3-live验收.json`。
